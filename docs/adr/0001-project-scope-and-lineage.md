# ADR-0001: 项目定位、目标态与 legacy 边界

- **状态**：已接受（**第 2 版**，2026-10-25 重写；第 1 版在 [`archive/`](./archive/0001-project-scope-and-lineage.md)）
- **日期**：2026-10-25
- **相关**：全部其他 ADR —— 本 ADR 定义它们共同的前提

## 背景

要的是一个**能真实跑、能演示的大模型 API 网关 + Agent 编排平台**，不是 demo 壳。

来源项目 `legacy/`（JAiRouter v3.4.0）实测规模：

| 项 | 事实 |
|---|---|
| 主代码 | 819 个 `.java` / 149,148 行 |
| 测试 | 426 个文件 / 4,266 个 `@Test` |
| 前端 | 92 个 `.vue` / 约 5.1 万行 |
| 技术栈 | Java 17 + Spring Boot 3.5.5 + WebFlux + JPA + Flyway + Caffeine/Redis |
| 许可 | Apache-2.0，293 处 `@author JAiRouter Team` |
| Git 历史 | 仅 1 次提交且几乎为空 —— **没有可继承的提交历史** |

没有历史可继承，意味着「保留上游提交链条」这个选项根本不存在，唯一形态就是把代码当素材处理。

**为什么这篇要重写。** 第 1 版写于「骨架能不能立住还不知道」的时候，因此它的核心结论是「不追求功能对等」——
那是在未知前提下的正确收敛。现在骨架已经立住并交付（一个 Face、两种 wire 形态、熔断与结算闭环、
契约测试与结构规则、120 个测试），未知项消失了，目标态随之改变：

> **目标态 = legacy 的能力面**。九类能力（适配器 / 负载均衡 / 规则 / 韧性 / 配额 / 记录治理 /
> 可观测 / 持久化与多副本 / 控制台）逐项对齐，实现自建。

目标从「验证骨架」变成「补齐能力面」，是整套 ADR 重写的原因，也是本 ADR 取代第 1 版的理由。

## 决策

### 1. 目标态以 legacy 能力面为准，不以「功能对等」为准

对齐的是**能力面**（有没有这一类能力、它在链上的位置对不对），不是**实现细节**（配置键叫什么、
页面怎么排、表结构是否兼容）。差别是具体的：

- 能力缺了要补 —— 缺负载均衡就是缺，没有讨价空间
- 「legacy 有 20 张表、我们也得有 20 张」不算对齐，那是搬运

因此目标态是一张**能力清单**，而不是一份差异对比表。清单见本 ADR 第 7 节，也是排期的唯一依据。

### 2. legacy 是设计素材库：逐项裁决，而不是一律不搬或一律搬

**「不搬运 legacy 代码」与「直接搬过来」都是错的。** 前者把 149k 行里经过生产验证的部分
（限流 Lua 脚本、6 种负载均衡策略、无锁熔断状态机、`usageStrict` 语义）当成不存在，
代价是重新踩一遍它踩过的坑；后者会把缺陷一起搬进来（两套限流、4 套 store、缺失的流式终态）。

每一项 legacy 能力按四类裁决，**逐项写进 `docs/planning/legacy-review.md`**：

| 裁决 | 判据 | 例子 |
|---|---|---|
| **搬** | 实现正确、新架构下有对应位置、改的是坐标与契约而不是机制 | 限流四算法与 Lua 脚本、LB 策略集、`LockFreeCircuitBreaker` 的无锁状态机、Flyway 迁移骨架与热路径索引、脱敏规则引擎的「规则 / 引擎分离」、调用历史三档与 AES-256-GCM、运维资产（Grafana / Prometheus / Loki / K8s / compose / 审计脚本）、前端页面 |
| **改** | 方向对但有实质缺陷，改缺陷而不改机制 | 流式终态上报（见 [0006](./0006-streaming-terminal-outcome-contract.md)）、SSE 逐帧脱敏、两套限流合一（见 [0007](./0007-traffic-governance-model.md)）、4 套 store 收敛为 1 套（见 [0012](./0012-storage-migrations-and-cluster.md)） |
| **新增** | legacy 没有，本项目需要 | 服务 / 实例 / 适配器的运行时注册表（[0013](./0013-configuration-model-and-runtime-registry.md)）、契约测试与结构规则（[0008](./0008-verification-and-quality-gates.md)）、Agent 层 |
| **不搬** | 收益撑不住复杂度，或缺陷与实现绑定无法局部改 | 160 个自研 tracing 类、向不存在端点推全量配置的 `HttpConfigPushService`、遮蔽 `/actuator/metrics` 的自研 Controller、4 套配置版本服务、186 行 checkstyle 抑制文件 |

### 3. 搬进来的代码必须过三道关

搬不等于粘贴。每一项搬运都要满足：

1. **换坐标**：包名迁到 `io.github.airouter.*`，类名与术语按 [`GLOSSARY.md`](../../GLOSSARY.md)
   （`Adapter` 这种语义含糊的旧词必须消解成 Face 或 Provider）
2. **适配新契约**：治理组件的输入只有 `Outcome`（[0006](./0006-streaming-terminal-outcome-contract.md)）；
   `core` 依赖树零框架（[0003](./0003-module-structure-and-dependency-direction.md)）；
   Jackson 3 单 classpath（[0002](./0002-tech-stack-and-version-pinning.md)）；构造函数注入，不用 `@Lazy` 压环
3. **补它原来没有的测试**：legacy 的测试是「4 个 `@SpringBootTest` + 全 mock + 被环境变量关掉的真实依赖测试」，
   它验证了「我调用了我以为我要调用的东西」，没有验证行为。搬进来的每一处至少要补上**失败路径**与**依赖缺席路径**的断言

**留痕**：搬进来的文件在提交信息或评审记录里写明来源文件与改动点。这条的目的不是流程，
是让三年后有人能回答「这块为什么长这样」。

### 4. 保留署名

上游是 Apache-2.0。搬运进来的文件保留原有 `@author` 与版权头；README 顶部写明来源仓库、原作者与 License。
删除署名不是二开的必要条件，反而引入合规问题。

### 5. 阶段排期：先建实例维度，再广度铺开，控制台最后

**先广度后深度**：Phase B 把九类各铺一层（每类都能用、都有测试），Phase C 再回头把核心链路做深。
控制台放最后，且是**适配 legacy 前端**而不是重写页面。

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| **A 地基** | 存储与迁移（[0012](./0012-storage-migrations-and-cluster.md)）→ 配置模型与注册表（[0013](./0013-configuration-model-and-runtime-registry.md)）→ 实例选择链（[0007](./0007-traffic-governance-model.md)） | 「一个请求进来 → 选中一个实例」这条链真的存在，且链上每一环可单独断言 |
| **B 广度** | 九类各铺一层：负载均衡补全、规则路由、限流内核、失败转移、响应缓存、配额账本、调用历史、认证与 RBAC、可观测性、多副本、适配器扩展 | 每类都能用、都有测试；**依赖缺席路径必测** |
| **C 深度** | 治理深化（自适应阈值、EWMA 调优、维度细化、配额对账）、配置版本与回滚深化 | Phase B 结束后立刻排期，不得无限延后 |
| **D 控制台** | 管理面 API 契约收口 + 契约测试钉住 → 适配 legacy 前端 | API 形状先被契约测试钉住，再接前端 |

**为什么 Phase A 不是限流**：限流的作用域是 `service / instance / client`，而这三个标识在实例维度
建立之前都不存在。那时做限流，做出来的是一个全局开关，不是限流。

排期不是本 ADR 要锁定的决定（它会随实施调整）；**被锁定的只有顺序约束**：实例维度先于一切作用域类功能，
控制台后于管理面 API 契约，Phase C 紧接 Phase B。

## 目标态能力清单

| 能力 | legacy 现状 | 我们此刻 | 目标态 |
|---|---|---|---|
| 适配器 | 9 个内置，其中仅 Ollama / Gemini / Claude 为真实现，其余是同一套 OpenAI 兼容 + 默认地址差异 | 2 种形态（`openai` / `ollama`），单端点 | 形态自述扩展；兼容厂商由配置承担，原生形态才写 codec（[0009](./0009-second-wire-shape-and-shape-self-description.md)） |
| 负载均衡 | 6 种：`random` / `round-robin` / `least-connections` / `ip-hash` / `consistent-hash` / `latency`（EWMA）。另有一个粘性包装器与一个缓存权重选择器，不是独立策略 | 不存在（只有一个实例） | 策略集搬到 `select`，纯函数、可确定性断言（[0007](./0007-traffic-governance-model.md)） |
| 规则路由 | 条件路由 + 命中统计 | 不存在 | 首命即止、优先级稳定；命中只在决策生效点计数一次 |
| 韧性 | 熔断 / 失败转移 / 限流 / 缓存；限流两套并存零共享 | 熔断与可用性闸门已有；结算闭环已有 | 失败转移、缓存补齐；限流与配额合成一个内核 |
| 配额 | 4 段 Lua + `usageStrict`（读不到用量绝不当 0）+ fail-open 分层 | 不存在 | 搬 Lua 与 `usageStrict`；fail-open 分层改为显式契约 |
| 记录治理 | 调用历史三档 + AES-256-GCM | 不存在 | 搬结构与加密方案；解密端点仅 ADMIN，密文不含明文回退 |
| 可观测性 | 指标 / 链路 / 慢查询 / 告警（160 个自研 tracing 类） | 健康端点与在途计数 | 用 Micrometer / OTel starter 取代自研；**告警只出指标与日志**，仓内不实现推送通道 |
| 持久化 | H2 / PG + Flyway；4 套 store + 4 层 tier | 不存在 | 一次到位：H2 默认 / PG 按 `DATABASE_URL`；store 只有一套，且 DB / Redis 缺席必须可降级（[0012](./0012-storage-migrations-and-cluster.md)） |
| 多副本 | 事件广播 / 共享计数 / 分布式锁 | 不存在 | 依赖 Redis；缺席时退化为单机语义并明确记日志 |
| 控制台 | 92 个 `.vue`，全项目最贵资产 | 不存在 | 最后做；适配而非重写，前置条件是管理面 API 契约已钉住 |
| 认证与 RBAC | 63 个权限码 / 83 条 URL 规则 / 4 个角色模板，双轨且 WebFlux 下类级 `@PreAuthorize` 不可靠 | 不存在 | 先分类建台账，按需实现；保留 URL 矩阵这一条轨；**`X-API-Key` 绝不透传下游**（legacy 无测试，我们必须有） |

## 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 一律不搬 legacy 代码 | 149k 行里经过验证的部分（Lua 脚本、LB 策略、无锁熔断、`usageStrict`）被当废纸；代价是重踩旧坑，收益是零 |
| 一律搬（追求功能对等） | 缺陷与实现绑定（两套限流、4 套 store、缺失的流式终态），搬进来等于把修好的问题再修一遍；且大量预算消耗在对齐配置键与页面布局上 |
| 只做外层包装、内部机制不动 | 最严重的问题正在机制里（流式结果上报、脱敏路径），包一层壳修不掉 |
| 抹去来源痕迹当作自有作品 | Apache-2.0 要求保留署名；293 处署名痕迹客观存在，声称原创经不起核对 |
| 先做限流 / 先做控制台 | 前者缺作用域标识，后者缺稳定 API 契约，都是把依赖倒置 |
| 阶段排期写进独立路线图文档、与 ADR 分离 | 顺序约束（实例维度先于作用域类功能）是一条**会被人想推翻**的决定，属于 ADR；排期细节只是它的载体 |

## 后果

**正面**

- 目标态是一份可勾选的清单，不是一句愿景；做完没做完可以逐项判定
- 搬运有判据、有留痕、有过关条件，「要不要顺便改一改」不再靠个人判断
- 控制台后置，前端接的是已被契约测试钉住的 API

**负面与风险**

- 「逐项裁决」意味着读 legacy 的时间躲不掉：九类能力至少各要一次通读才能判搬不搬
- 搬进来的代码质量参差，容易出现「搬完就当完成」——第三道关（补测试）是唯一防线，它也是最容易被跳过的
- 能力清单会膨胀：legacy 有而我们要不要有的，每一条都要给结论，否则清单退化成待办垃圾场
- 阶段排期放在 ADR 里意味着它会变，而 ADR 变更成本高于普通文档。缓解方式：本 ADR 只锁**顺序约束**，
  阶段内的细节调整不需要动 ADR

## 如何验证

- [ ] `docs/planning/legacy-review.md` 对每一项 legacy 能力都给出四类裁决之一与理由
- [ ] 每一个搬进来的文件在提交信息或评审记录里写明来源文件与改动点
- [ ] 搬进来的代码至少有一条它原本没有的失败路径或依赖缺席路径断言
- [ ] `legacy/` 不在根 POM 的 `<modules>` 里，CI 不扫描该目录
- [ ] README 顶部写明来源仓库、原作者、License 与二次开发声明
- [ ] 搬运进来的文件保留原有 `@author` 与版权头
- [ ] 目标态能力清单里每一项的「目标态」列都不是空的（空 = 没裁决）
