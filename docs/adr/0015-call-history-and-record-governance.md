# ADR-0015：调用历史与记录治理

- 状态：已接受
- 日期：2026-10-26
- 相关：[0017](./0017-persistence-migrations-and-multi-replica.md)（落库）、[0016](./0016-observability-metrics-tracing-and-alerts.md)（元数据也是指标源）

能力面：**第 6 类（记录治理）**

## 1. 三档

| 档位 | 记什么 | 用途 |
|---|---|---|
| `metadata` | 仅元数据：时间、服务、实例、形态、租户、耗时、用量、成败 | 默认档。足够做统计、计费、排查 |
| `summary` | 加上请求/响应的**脱敏后摘要** | 需要知道「问了什么」但不需要原文 |
| `full` | 请求与响应**完整**记录，AES-256-GCM 加密后落库 | 审计与争议处理 |

**默认 `metadata`**，可按服务单独配置。三档是**范围递增**关系，不是互斥选项。

## 2. 脱敏

- 内置规则：手机号、邮箱、身份证、银行卡；支持自定义正则
- 规则可配置、可持久化（legacy 的 `V4__sanitization_config.sql` 就是这张表，可搬）
- **脱敏失败必须 fail-closed：拒绝记录，不能「记原文」。**
  > 那样脱敏配置写错就等于明文落库，而且没有任何日志说明为什么

## 3. 加密全文

- **AES-256-GCM**。密钥来自环境变量，不进配置文件、不进代码
- 每条记录**独立 IV**；AAD 绑定记录主键（防止整条密文被替换成另一条）
- **解密端点仅 ADMIN 角色**，且解密动作本身要记审计（谁在什么时候解了哪条）
  > 解密是一个高危动作：能读明文的人必须可追溯

## 4. 与流式的关系

- 调用历史在**终态**写一次（与结算同点，见 [0005](./0005-streaming-terminal-outcome-contract.md)）
- 失败转移只写最终那一次的主记录
- `full` 档下，流式响应需要先累积完整内容 —— 受 `BoundedAccumulator` 上限约束：
  **截断影响展示，不影响计费**（token 估算走独立的字符计数轨道）

## 5. 留存与清理

- 三档都可配留存期，过期按档位清理（`full` 的留存期应显著短于 `metadata`）
- 清理是定时任务，多副本下**必须加分布式锁**（[0017](./0017-persistence-migrations-and-multi-replica.md) 第 5 节）

## 6. 裁决

| legacy 的东西 | 裁决 |
|---|---|
| 三档模型 | **搬**（这是它少数设计得当的地方） |
| `V4__sanitization_config.sql` 脱敏配置表 | **搬** |
| AES-256-GCM 全文加密与 ADMIN-only 解密端点 | **搬**（改：AAD 绑定主键、密钥只从环境变量） |
| 脱敏失败的处理 | **新增** —— legacy 没有明确口径，这是必须补的失败路径 |

## 7. 验收

- 三档各有一条端到端断言（落库内容符合该档的定义）
- 脱敏规则写错（非法正则）→ 拒绝记录且报出具体规则，不是静默记原文
- `full` 档：库里查不到明文（断言密文形态）；ADMIN 能解、非 ADMIN 被拒
- 解密动作有审计记录
- 流式与非流式在同一档位下记录的字段一致
