# 05: 非流式端到端打通 + wire format 契约测试基础设施

> 来源：[spec.md](../spec.md) — 用户故事 1、5、7、8、29

**What to build:** 一条真实的 chat 请求从 OpenAI 兼容的 Face 进入，翻译成 `CanonicalRequest`，由 Provider 转发到真实模型端点，响应被翻译回来并以 OpenAI 兼容的 JSON 返回 —— 一个现成的 OpenAI 客户端库无需改动就能解析它。同时把 golden-file 对照基础设施就位。

这是本次 P0 的第一条真正的垂直切片：从 HTTP 进、从 HTTP 出，中间穿过全部四层。它同时也是后续从 `legacy/` 搬运代码的前提 —— Jackson 2 → 3 最危险的产物是「编译通过但序列化行为变了」，没有这组基线文件，那种变更无从发现。

**Blocked by:** 03 质量门禁、04 app 启动

**Status:** ready-for-agent

- [ ] 向 `/v1/chat/completions` 发送 `stream=false` 请求得到 200，响应体可以被标准 OpenAI 客户端库直接解析
- [ ] 请求中携带厂商私有字段时被原样转发，上游响应的厂商独有字段也被完整透传给调用方（用携带一个越界字段的请求验证）
- [ ] 每次响应都携带可用于排查的请求标识，成功路径与失败路径都出现
- [ ] 上游提供 usage 时如实返回；上游未给出 usage 时该字段缺失而不是被编造
- [ ] golden-file 对照基础设施就位：给定录制的上游字节，产出的响应体与存储的期望值比对，不一致时构建失败并给出差异
- [ ] 第一组基线文件至少覆盖：正常非流式响应、上游返回 4xx、上游返回 5xx
- [ ] 新增一个用例不需要改任何代码，只需要放入输入与期望两份文件
- [ ] 上述全部断言都从入站 HTTP 边界做出，不 mock 任何内部组件
- [ ] 是否要走 Canonical 中间表示这件事是可见的：Face 侧与 Provider 侧都不持有对方的 wire 结构知识
