# 05: 字节边界与块间不变量

**What to build:** 无论上游怎么切分字节块，读出来的内容都一模一样；
一个多字节字符被切在两个 TCP 段之间也仍然正确。

分帧器是 wire format 的入口，而它的行为只在上游**恰好**那样切分时才会出错 ——
真实端点给不出这些切分方式，所以本票全部断言都由录制器按字节块喂出来。

**Blocked by:** 03

**Status:** ready-for-agent

## Acceptance criteria

- [ ] 一个多字节字符被切在两个 TCP 段之间时仍能正确合并（中文响应不在块边界乱码）
- [ ] 空 `data:` 帧被忽略，不当成内容（上游保活不污染输出）
- [ ] `Ping` 不影响终态判断 —— 保活既不冒充内容，也不冒充结局
- [ ] 一次流式 pipeline 中同一个块被解析的次数（`CHUNK_PARSE_COUNT`）**恒为 1**
- [ ] 任意分块方式下合并结果唯一（property-based：用生成式输入断言不变量）
- [ ] 以上全部在**可用的最高接缝**（HTTP 入口）上完成，
      由录制器以字节块列表加块间间隔喂入，在 HTTP 出口断言

## Notes

- 本票的「纵向」体现在：字节 → 帧 → 事件 → 合并结果 → 客户端输出，
  一整条链都穿过，不是分帧器单层的单元测试
- 录制器需要的能力：以**字节块列表加块间间隔**回放、报告收到的请求次数与写出的块数
  （形状见 tag `baseline-pre-11`）
- 真 Ollama 的用途是抓样本，不进本票的常规测试
- 测试文件并入模块预算，需合并同类项
