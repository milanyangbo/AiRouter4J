# 04: 流式终态与结算

**What to build:** 上游不讲完就不是成功；客户端取消不产生事件但仍然结算；
一条流恰好结算一次。

这是全套 ADR 里最重要的一条纪律的落地。legacy 最贵的缺陷就是它：
响应头写出成功就记为成功，于是一个持续吐出半截响应的实例，在它的口径里是 100% 成功。

**Blocked by:** 03

**Status:** ready-for-agent

## Acceptance criteria

- [ ] `Terminal` / `Failed` 是终态的**唯一**形态，由 Provider **显式**发出，
      不允许依赖 `onComplete` / `onError` 隐式推断
- [ ] 上游收了连接但没发结束哨兵 → 补发 `Failed(upstream_closed)`，**不是** `SUCCESS`
      （内容是否完整无从判断）
- [ ] 帧间静默超过 `idleTimeout` → `UPSTREAM_TIMEOUT`
- [ ] 客户端中途断开 → **无事件**（接收方已经不在了），但**必须结算**成 `CLIENT_CANCELLED`
- [ ] `OutcomeObserver` 是结算的**唯一**收口点；本阶段它接到一个可观测的结算记录上
- [ ] 结算记录能区分四种 `OutcomeKind`，于是「取消不会冒充失败」是可被断言的
- [ ] 一条流**恰好结算一次**（`StreamState.claim()` 第二次返回 false）
- [ ] `usage` 优先取上游回报，取不到时才讨论本地估算
- [ ] 累积内容有上限且超限截断；**截断影响展示，不影响计费**
      （token 估算走独立的字符计数轨道）
- [ ] 只有 Provider 能构造 `Outcome`（R9）；`routing` / `governance` 看不到 HTTP 状态码（R4）

## Notes

- **本阶段不交付熔断器本体**（它属阶段 7）。本票的交付是结算点与结算记录；
  熔断器接进同一个 `OutcomeObserver` 时，「取消不计入熔断」自动成立
- **「本地拒绝不出网、不结算」不在本票** —— 它需要注册表与可用性闸门，属阶段 3
- 故意制造上游失败的用例**必须交代它与熔断阈值的关系**：默认阈值是 3，
  同一测试类里三条失败就会把熔断器打开，于是后面某条用例收到的是
  `instance_unavailable` 而不是它想看的上游错误 —— 表现为一条**与执行顺序有关**的偶发红
- 时间相关的断言**等条件成立，不睡固定时长再比数字**
- 测试文件并入模块预算，需合并同类项
