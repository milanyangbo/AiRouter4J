# 13: 实例选择与选择链

> 来源：[ADR-0011](../../docs/adr/0011-feature-roadmap-and-migration-boundary.md) 决策 1

**What to build:** 把「一个请求进来 → 选中一个实例」这条链建起来，并让链上每一环的顺序
成为**被断言的事实**而不是调用顺序的巧合。本票先落三种策略（轮询 / 加权 / 随机），
其余四种在票 14 补齐。

链的形状：`已纳管 → 熔断未开 → 未限流 → 按策略选一个`。
前三步已经存在（`InstanceAvailability.accepts` 一次问完），本票要把它从「一个实例」
推广到「一组实例里挑一个通过的」。

**Blocked by:** 12 服务 / 实例 / 适配器配置模型与运行时注册表

**Status:** todo

- [ ] 选择链：先过滤（健康纳管 / 熔断 / 限流），再从**通过过滤的集合**里按策略选一个；
      **不是**先选后判——先选后判会让「选中的那个不健康」变成随机成功
- [ ] 三种策略：轮询、加权、随机。策略可配到服务上，缺省时有明确默认值并写进启动日志
- [ ] 选择与判闸的顺序被断言：过滤集为空时**快速失败且不产生上游调用**
      （与 `AvailabilityGate` 拒绝时不结算同一纪律）
- [ ] 加权是工具而不是独立策略：它嵌在轮询与随机里（legacy 的 `WeightCalculator` 做法），
      避免「加权轮询 / 加权随机」两个类各写一遍权重逻辑
- [ ] 多实例端到端：起两个录制上游，断言流量分布符合策略，且摘掉一个之后流量全到另一个
- [ ] 选择结果可观测：这一次选中了谁、过滤掉了几个、因什么被过滤，进结算与指标

## 实现要点（来自 legacy 的教训）

- legacy 的 `RandomLoadBalancer` 里**内嵌了第二套熔断器**（硬编码阈值），
  而 LB 实例是用 `new` 创建的，于是 `@Autowired(required=false) MetricsCollector` 恒为 null、
  指标静默丢失。我们的 LB 必须由容器创建，且**不自带熔断**——熔断只在 `InstanceAvailability` 那一处。
- 规则可以覆盖 LB 策略（legacy 的 `LB_STRATEGY` 动作），那条路径每次 `new` 一个 LB。
  我们的策略对象应当是无状态的可复用对象，选择时才传入实例集合。
- EWMA / 连接数 / 熔断态都是**内存态**，重启即失。票 14 做 EWMA 时要明确写出这个事实，
  不要让它看起来像是持久化的。
