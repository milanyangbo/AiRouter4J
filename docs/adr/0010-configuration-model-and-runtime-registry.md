# ADR-0010：配置模型与运行时注册表

- 状态：已接受
- 日期：2026-10-26
- 相关：[0009](./0009-adapters-shape-factory-and-vendor-declaration.md)（形态工厂）、[0011](./0011-instance-selection-and-load-balancing.md)（选择链消费注册表）

能力面：**第 1、2 类的共同地基**（也支撑 3–8 类的作用域维度）

## 1. 三级模型

```
Service（逻辑服务名，如 chat / embedding）
  └ ModelInstance（实例）
       ├ id、权重、启用标志、标签
       ├ Endpoint（baseUrl / 凭证 / 超时）
       ├ shape（形态：openai / ollama / anthropic / gemini）
       └ vendor（厂商：仅影响默认地址与转换点）
```

- **形态是实例的属性，不是全局设置。** 同一 Service 下两个实例可以有不同形态 —— 合法配置
- **实例维度先于一切作用域类功能**（[0001](./0001-scope-target-state-and-sequence.md) 第 5 节）：
  限流作用域、规则目标、失败转移换谁、配额维度，全部以这一层为前提

> **实现补充（阶段 3，票 07）**：实例集合用**列表 + 显式 id**，不用 `Map<id, Instance>`。
> Map 的键不可能重复 —— 写错的第二个会静默覆盖第一个，而第 4 节要求「id 重复」在启动期判红。
> 列表的代价是 Spring Boot 绑定**列表元素**时不跨配置来源合并：
> 在命令行只覆盖 `instances[0].base-url`，那个实例的其余字段不会被配置文件补齐，
> 结果是「id 缺失」这样一个指向错误的报错。因此要改其中一个字段，
> 必须在同一个配置来源里把这个实例写全（`application-local.yml` 就是这么做的）。
> 这一条也写进了 `AGENTS.md`，因为它是配置写法而不是模型选择。

## 2. 注册表是唯一持有者

`registry` 持有「配置 → 运行时对象」的映射：服务、实例、Provider 实例，
以及挂在实例上的**熔断状态、延迟样本、健康登记**。

其它包不自己缓存这些东西 —— 一旦有两处持有，热重载必然漏改一处。
> legacy 的 `ModelServiceRegistry` 是同一件事，但它的实现**同时承担了选择与粘性路由**，
> 那不是注册表该做的事。可搬的是「唯一持有」这个约束，不是那个类。

## 3. 配置来源与优先级

| 来源 | 用途 | 优先级 |
|---|---|---|
| 环境变量 | 凭证、baseUrl（**唯一**允许出现真实凭证的地方） | 最高 |
| 配置文件（yml / profile） | 服务与实例的结构、权重、策略 | 中 |
| 数据库 | 运行时可变更的部分（规则、厂商声明、实例开关） | 低（可被管理面改） |

**配置文件里不得出现 API 密钥**，一律走环境变量。
**凭据不透传给下游**：出网时用的是实例自己的凭证，不是调用方带来的那把。

## 4. 启动期校验

以下情况在**启动期**判红，不留到运行期：

- 形态要求的凭证缺失
- baseUrl 不符合形态约定的后缀（缺 `/v1` 或 `/api`）
- 同一 Service 下实例 id 重复
- 引用了未声明的厂商

> 缺 `/v1` 在 Spring AI 2.x 下不在启动期报错，只会变成一次运行期的 404 —— 所以它必须是我们自己加的校验。

## 5. 热重载不重建 Spring 上下文

配置变更时**只替换注册表里的对象**。重建上下文会丢掉在途的流、熔断计数与延迟样本 ——
一次配置变更等于一次全站状态清零，那是重启，不是热重载。

在途请求继续用它开始时拿到的那一份对象，直到结束。

> **实现补充（阶段 3，票 08）**：三步，顺序固定 ——
> **先装配**（`InstanceAssembler` 算出一版新的服务视图）、**再记账**（`ConfigurationLedger` 前进版本号）、
> **最后换注册表**（`UpstreamRegistry.replace` 一次引用赋值）。反过来的次序会在装配抛异常时留下
> 「账本说 v2 生效过，而注册表里还是 v1 的东西」这样一处对不上的账。
>
> 「在途请求不受影响」不需要额外代码：请求在开始时取走的是**具体的出网对象**，不是注册表本身，
> 换掉注册表影响的是下一次取用。因此给 Face 的那一份端口是**每次请求解析当前生效的那一版**
> 的（`UpstreamConfiguration.upstreamProvider`）—— 装配时固定下来的话，一次热重载对这条路径
> 完全无效，请求会一直打给已被换掉的实例。
>
> **只换该换的**：判定的依据是 `OutboundIdentity`（形态 / 地址 / 凭证 / 模型 / 超时）。
> 权重、启用标志、标签不在里面 —— 它们改的是怎么挑这个实例，不是它怎么出网。
> 于是「改权重」与「关掉再打开」都沿用同一个出网对象，挂在它上面的运行时状态
> （熔断计数、延迟样本）因此活过配置变更。这是本阶段能给出的「状态不丢」的机制：
> 状态尚未落地（阶段 7），但它的**宿主**已经不会被无谓地换掉。

## 6. 配置版本与回滚

每次配置变更产生一个**不可变快照**，带版本号。它回答两个问题：现在生效的是哪一版、能回滚到哪一版。
多副本之间广播的是「变更事件 + 版本号」，**不是全量配置**。

> legacy 的 `HttpConfigPushService` 把全量配置推给一个并不存在的端点，**不搬**。

版本快照的持久化随 [0017](./0017-persistence-migrations-and-multi-replica.md) 的表结构落地。

> **实现补充（阶段 3，票 08）**：**版本号只增不减，回滚也是一次变更** ——
> 回滚产生新的一版，其内容取自要回到的那一版。另一条路（让版本号回退）会让副本之间
> 无法用「版本号大的新」判断谁落后，而广播的恰恰只是版本号；单调的版本号顺带就是一条变更史
> （v7 与 v3 内容相同，说明第 7 次是一次回滚）。
>
> 内存里只留最近 16 版（`ConfigurationLedger.RETAINED_VERSIONS`）：无限增长的变更史在长跑的
> 进程上是一个缓慢的泄漏，而回滚不需要三个月前的那一版。落库之后这个上限由表承担。
>
> 两个已知代价：① 快照里带着实例自己的凭证，于是历史里也留着旧值，凭证轮换之后旧值在内存里
> 还会存在一段时间 —— 落库时这一条要一并处理；② 广播本身随阶段 13 落地，本票只把「版本号单调」
> 这个前提做好，到那一天不需要回来改它。

## 7. 验收

- 配置变更后：在途的流不受影响；熔断计数与延迟样本不丢失
- 两个不同形态的实例共存于一个 Service，且被端到端测试覆盖
- 环境变量缺失时启动失败，且失败信息指向具体实例与形态
- 回滚到上一版后，运行时对象回到上一版的等价状态

> **实现补充（阶段 3，票 08）**：「熔断计数与延迟样本不丢失」在**状态尚未落地**（阶段 7）时，
> 验收的是它的**机制**：改权重 / 改启用标志 / 改标签不换出网对象（`RegistryReloaderTest`
> 断言前后是同一个），改地址则换。状态挂到出网对象上那一天，这一条就自动变成它字面上的意思。
>
> 「不重建上下文」在本阶段的证据是**进程学到的东西还在**：结算账本在变更之后仍保留变更之前的
> 记录，且它还是同一个 bean（`ReloadEndToEndTest`）—— 重建上下文会另起一本空账。
