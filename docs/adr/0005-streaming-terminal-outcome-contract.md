# ADR-0005：流式终态与结算契约

- 状态：已接受
- 日期：2026-10-26
- 相关：[0004](./0004-canonical-intermediate-representation.md)、[0013](./0013-resilience-circuit-failover-ratelimit-cache.md)

> **这是全套 ADR 里最重要的一篇。** legacy 最贵的缺陷是「流式路径绕过治理」：
> 响应头写出成功就记为成功，熔断、结算、配额都看不到真正的终态。
> 一个实例持续吐出半截响应，在 legacy 的口径里是「100% 成功」。

## 1. 决定：终态由 Provider 显式发出

- `CanonicalStreamEvent.Terminal / Failed` 是终态的**唯一**形态
- 终态**必须显式发出**，不允许依赖 `onComplete` / `onError` 隐式推断
- 终态是这条流的**最后一个**事件；终态之后的帧不出现在客户端

## 2. 结算的唯一收口点

`OutcomeObserver` 是**唯一**的成功/失败/取消观测点。
所有协作组件（熔断器、EWMA 延迟样本、指标、配额结算、调用历史）都只从这里取结果，
**不得各自观测**（R4 / R9 判红：治理组件读状态码、读异常类型、或自己造一个 `Outcome` 都会让构建变红）。

一条流**恰好结算一次**，由 `StreamState.claim()` 保证。

## 3. 终态来源矩阵

| 情形 | 事件 | `OutcomeKind` | 计入熔断 |
|---|---|---|---|
| 上游正常结束 | `Terminal` | `SUCCESS` | 否 |
| 上游返回 4xx/5xx | `Failed` | `UPSTREAM_FAILURE` | **是** |
| 上游收了连接但没发结束哨兵 | 补发 `Failed(upstream_closed)` | `UPSTREAM_FAILURE` | **是** |
| 帧间静默超过 `idleTimeout` | 补发 `Failed(UPSTREAM_TIMEOUT)` | `UPSTREAM_TIMEOUT` | **是** |
| 客户端中途断开 | **无事件** | `CLIENT_CANCELLED` | **否** |
| 本地拒绝（熔断 OPEN / 未登记 / 限流拒绝 / 配额耗尽） | 无出网 | **不结算** | **否** |

四条容易写错的：

- **上游没发哨兵 ≠ 成功。** 内容是否完整无从判断，因此它是 `Failed` 而不是 `SUCCESS`
- **取消无事件但必须结算。** 接收方已经不在了，往断开的下游发事件不成立；
  但少记一次与记成成功，对熔断器是同一种误导
- **本地拒绝不结算。** 它不是一次上游调用；把它算作失败会让它继续喂熔断器，
  打开的熔断器就再也等不到冷却结束的那次成功探测
- **取消不计入熔断。** 用户关页面、移动端切后台都会产生取消；
  把它算作上游失败会让一次共享网络抖动熔断掉一个健康的实例

## 4. 延迟与用量的口径

- `latency` **一律算到收到终态为止**。这让流式与非流式的延迟具有可比性 ——
  否则「首个 token 很快」会被记成「这次调用很快」，P99 永远看不出问题
- `usage` 优先取上游回报；取不到时按 `usageStrict` 决定是否用本地估算（[0014](./0014-quota-multi-window-ledger.md) 第 3 节）

## 5. 失败转移与结算

换实例重试时：**只结算最终那一次**。中间尝试计入指标（重试次数、换过哪些实例），
但不重复扣配额、不重复写调用历史主记录。
> 「重试算几次结算」没有答案，是因为 retry 与 failover 被混成了一个词。术语表里两者分开，正是为了这条能写清楚。

## 6. 验收（每条都要有测试）

| 要守的事 | 断言 |
|---|---|
| 一条流恰好结算一次 | 同一 `requestId` 的 `claim()` 第二次返回 false |
| 未发哨兵即收连接 | 收到 `Failed`，错误类型 `upstream_closed`，**不是** `SUCCESS` |
| 帧间静默超时 | 收到 `Failed`，`OutcomeKind = UPSTREAM_TIMEOUT` |
| 取消 | 无事件；`OutcomeKind = CLIENT_CANCELLED`；熔断器计数不变 |
| 本地拒绝 | 无出网调用（假上游收到 0 次请求）；无结算 |
| 流式与非流式延迟可比 | 同一场景两种模式的 `latency` 在同一量级 |
| 流式路径不绕过治理 | 流式与非流式走同一条选择链（结构规则 + 端到端断言） |

## 7. 后果

- Provider 是唯一能构造 `Outcome` 的地方；其它包想判定成败就是设计错了
- 任何新增的治理组件都必须挂在 `OutcomeObserver` 上，不得另起一个观测点
