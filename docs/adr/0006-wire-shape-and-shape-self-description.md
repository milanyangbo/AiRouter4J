# ADR-0006：wire 形态与形态自述

- 状态：已接受
- 日期：2026-10-26
- 相关：[0009](./0009-adapters-shape-factory-and-vendor-declaration.md)（形态工厂与厂商声明）

## 1. 形态 ≠ 厂商

legacy 把这两件事混成一层，于是出现 9 个 Adapter 类，其中 6 个是同一套 OpenAI 兼容代码
只改了默认地址。**混层的代价是：新增一个 OpenAI 兼容厂商要写一个类。**

新版分开：

- **形态**（`UpstreamShape`）= 对面说哪一种**协议**：`openai` / `ollama` / `anthropic` / `gemini`
- **厂商**（vendor）= 上游的**身份**：Ollama / vLLM / GPUStack / Xinference / LocalAI / OpenAI / Anthropic / Gemini / Deepseek，以及声明式登记的任何一家

只有形态真正不同才需要新代码。**新增一个 OpenAI 兼容厂商是配置，不是类。**

## 2. 形态自述三件事

`UpstreamShape` 自己回答：

1. **地址该长什么样** —— OpenAI 兼容以 `/v1` 结尾，Ollama 原生以 `/api` 结尾，都不带尾斜杠
2. **这个协议要不要凭证** —— Ollama 原生不需要，其余需要
3. **流怎么结束** —— 经由各自的分帧器：SSE（`data:` + 空行 + `[DONE]`）还是逐行 JSON（末帧 `done:true`）

> Spring AI 2.x 不再自动补 `/v1` 后缀：少了它不在启动期报错，只会变成一次运行期的 404。
> 因此第 1 条是**启动期校验**，不是约定。
> 同一台本机 Ollama 两种地址都在 —— 这正是形态必须由配置显式给出、**不能按地址猜**的理由。

## 3. 分帧属于形态，不属于传输层参数

SSE 与逐行 JSON 是**并列的两种读法**，不是同一个读法的两种参数：

- SSE：以空行分隔事件，以 `[DONE]` 哨兵结束
- 逐行 JSON：每行一个完整 JSON，**没有** `data:` 前缀、没有空行、没有哨兵，靠末帧内容宣告说完

用 SSE 的读法去读逐行 JSON，**一条事件都产不出来**（解析次数为 0）。
这一条必须有断言 —— 它是「两种读法并列」这个判断唯一能被证伪的地方。

## 4. 措辞归形态

错误文案、术语、以及「什么算异常结束」的解释，都由形态自己提供（`ErrorExplainer` 之类的自述位），
**不写在共享的错误映射里**。

> 踩过的坑：为了改一处文案动了共享映射，结果另一个形态的 golden 基线一起变红。
> 措辞是形态的属性；把它放进共享层，等于让两个形态的契约互相耦合。

## 5. 形态差异只留在「一帧字节 → 哪些事件」

分帧之后的所有处理（累积、结算、熔断、指标）**与形态无关**。
形态差异唯一该存在的位置是 `providers/<形态>/` 里的 codec。

## 6. 新增一种形态要动的地方

1. `providers/<形态>/` —— codec 与 provider
2. `transport` —— **只有当分帧方式不同时**才加一种读法
3. `UpstreamShape` —— 加一个取值
4. 形态工厂 —— 登记一个构造器

`faces` 与 `core` **不在这个列表里**。它们一旦出现，说明抽象体表错了：回来修抽象，
不要接受那份改动 —— 由 `SecondProviderTouchesNoFaceTest` 用差异统计判红。

两条路的共同点：**形态差异由配置或登记决定，不在调用路径上按形态分支。**

## 7. 后果

- 9 个厂商里只有 3 个（ollama / anthropic / gemini）需要真代码，其余是配置声明
- 新增厂商不改任何 Java 文件；新增形态才改，且改动范围被第 6 节限定
