# 05: 字节边界与块间不变量

**What to build:** 无论上游怎么切分字节块，读出来的内容都一模一样；
一个多字节字符被切在两个 TCP 段之间也仍然正确。

分帧器是 wire format 的入口，而它的行为只在上游**恰好**那样切分时才会出错 ——
真实端点给不出这些切分方式，所以本票全部断言都由录制器按字节块喂出来。

**Blocked by:** 03

**Status:** done（`baseline-4`）

## Acceptance criteria

- [x] 一个多字节字符被切在两个 TCP 段之间时仍能正确合并（中文响应不在块边界乱码）
- [x] 空 `data:` 帧被忽略，不当成内容（上游保活不污染输出）
- [x] `Ping` 不影响终态判断 —— 保活既不冒充内容，也不冒充结局
- [x] 一次流式 pipeline 中同一个块被解析的次数（`CHUNK_PARSE_COUNT`）**恒为 1**
- [x] 任意分块方式下合并结果唯一（property-based：用生成式输入断言不变量）
- [x] 以上全部在**可用的最高接缝**（HTTP 入口）上完成，
      由录制器以字节块列表加块间间隔喂入，在 HTTP 出口断言

## 落点

全部并进既有的 `StreamingEndToEndTest`（18 个 `@Test` + 1 个 `@TestFactory`，上限 20），
**没有新增测试文件** —— app 的测试文件数已是预算上限 10。main 代码**一行未改**：
字节层缓存与空帧忽略在票 03 就写对了，本票是把它们变成会被红的事实。

录制器加了一条能力：`replayBytes(List<byte[]>, Duration)`。

## 三条值得记住的判断

### 1. 造「多字节字符被劈开」必须走字节，不能走字符串

一个三字节的汉字被劈成两半之后，两半各自都**不是合法文本**。
用 `List<String>` 表达就等于在编码层先把字符修好了 —— 那正是要被证伪的那个假设。
所以录制器把块存成 `byte[]`，`replayStream(List<String>, ...)` 退化成它的一条便捷入口。

### 2. 不留间隔的切分等于没有切分

`between = ZERO` 时内核会把相邻的小块合成一个 TCP 段，「切在两个段之间」根本没有发生 ——
测试看起来在测分块，其实测的是合并后的那一段。所以真正要断言的切法都留了 200ms 的块间隔
（`SEGMENT_GAP_MS`）；一个字节一块那一种留 1ms，图的是一次覆盖所有切点而不是每一块都真的成段。

同一个循环里三个切点中有一个是**对照**（切在字的起始字节处）。它存在的理由是：
破坏过的实现在这个切点上**仍然是对的**（第一次探红时 144/148 通过、149 才红），
没有对照就看不出「红是因为切在字里面」还是「红是因为分了块」。

### 3. `CHUNK_PARSE_COUNT` 不靠计数器断言

「解析了几次」没有外部可观测的计数器；为它往生产代码里塞一个计数器，
等于让测试决定生产代码长什么样。于是改成断言它在外的两个后果：

- 上游只被请求一次 —— 同一份字节没有被读两遍
- 每一块的内容在客户端恰好出现一次、顺序不变，帧数恰好等于「开场 + 内容 + 终态 + 哨兵」

第二条是重复解析在「译码 → 发事件」这条链上的**唯一**外在表现。
探红方式：把 `.concatMapIterable(decoder::decode)` 换成同一帧解码两次，
帧数 7 → 11，内容 `甲乙丙丁` → 重复。

## 故意破坏四处，都确认会红

| 破坏 | 红的断言 | 现象 |
|---|---|---|
| 分帧器先把块解码成字符串再拼 | 多字节切分 + property-based | `你好吗` → `���好吗` |
| 空 `data:` 帧被当成内容 | `emptyDataFramesAreNotContent` | 多出一帧空内容 |
| 注释帧被当成终态 | `keepaliveOnlyStream…` | 帧数 1 → 2，保活冒充了结局 |
| 同一帧解码两次 | `eachUpstreamChunk…` | 帧数 7 → 11，内容重复 |
