# 07: 终态契约：失败、超时、取消三类结算

> 来源：[spec.md](../spec.md) — 用户故事 4、6、15、17

**What to build:** 「上游报错」「上游超时」「调用方中途断开」这三种结束方式各自走到正确的终态上，且每种都恰好产生一个终态。调用方能区分「上游拒绝了请求」和「连接断了」这两种性质完全不同的失败。

注意本票验证的事实依据和一个已知缺口：本阶段的上游是真实模型端点，字节序列不可控，因此超时是通过把阈值调到极小来触发的，而不是靠真的等待。至于「流成功开篇后在中途静默断开」这类精确到字节的截断场景，在此 seam 下不可构造 —— 缺口已在 spec 中记录，留给后续引入可控本地上游时补齐。

**Blocked by:** 06 流式 SSE 路径与显式终态

**Status:** ready-for-agent

- [ ] 上游返回 4xx 时，调用方在 `[DONE]` 之前收到错误帧，错误结构与其他失败路径形态一致，但可区分为「上游拒绝了请求」
- [ ] 上游不可达时，收到同一套错误结构，可区分为连通性失败而非上游拒绝
- [ ] 超过 IdleTimeout 时补发 Failed 并把类别标为上游超时，即使上游从未说过话也有终态（通过把阈值调到极小来触发，不依赖真实等待）
- [ ] 调用方中途断开后不再收到任何帧；重复执行取消若干次后连接资源回收是稳定的（没有随次数增长的残留）
- [ ] 取消被记为 Cancellation 而不是 Terminal，且不会被归因成实例故障
- [ ] 上述每一条路径产生的终态数量都恰好是一，没有路径产生零个或两个
- [ ] 慢消费调用方不会导致网关侧出现无界缓冲（用一个刻意不读取的消费方验证积压有上界）
- [ ] 非流式路径走同一套错误结构与结算，不存在「只有流式才有这个错误形状」的情况
