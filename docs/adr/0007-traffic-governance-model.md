# ADR-0007: 流量治理模型

- **状态**：已接受
- **日期**：2026-10-23
- **相关**：[0006 流式终态](./0006-streaming-terminal-outcome-contract.md)（治理层的输入来源）、[0003 模块结构](./0003-module-structure-and-dependency-direction.md)

## 背景

来源项目的流量治理能力并不缺件 —— 限流、熔断、降级、健康检查、配额都有实现，
甚至包含 `LockFreeCircuitBreaker` 这样经过思考的并发设计。**问题不在缺，而在口径不一致。**

具体表现：

| 现象 | 后果 |
|---|---|
| 实例健康状态的默认值是**健康** | 一个从未被纳入健康管理的实例（配置漏项、刚注册未探测）会被当作可用节点接收流量。这是 fail-open |
| 本地计数器后端与 Redis 后端并存，两者的一致性语义没有统一定义 | Redis 故障时是否放行、放多少、本地额度如何与远端合并，取决于具体代码路径 |
| 同一个默认值在两个不同方法里被各自写了一遍，取值还不一致 | 不存在单一口径可查，改一处不会同步另一处 |
| 热路径表缺少索引 | `service_config` / `service_instance`（含外键）零索引，而 45 个索引里有相当比例建在日志表上 |

再加上 [0006](./0006-streaming-terminal-outcome-contract.md) 里那条：流式调用从不产生失败记录，
所以熔断器的输入本身就是残缺的 —— **在修复输入之前，讨论治理参数的调优是没有意义的。**

## 决策

### 1. 治理层的输入只有一个来源

熔断器、限流回放、健康检查、延迟统计，**全部只消费 `Outcome`**（见 0006）。
任何治理组件不得自己去看 HTTP 状态码、不得自己在 Reactor 操作符里判断成败。

这条既是设计约束也是代码约束，由依赖方向测试保证。

### 2. 默认 fail-closed

**未被纳入健康管理的实例，一律视为不可用。**

理由：一个不知道是否健康的节点，和已知故障的节点，对调用方造成的损害是一样的
（都是在把一个请求送进不确定的结果里）。fail-open 在这里没有任何收益，只有"看起来还在跑"的假象。

要放行某个实例，必须显式把它配置为可用并让其通过健康检查。这一条要有测试锁定。

### 3. 默认值集中定义

所有可用性相关的默认值集中在单一的 `AvailabilityPolicy` 里，不再散落。
测试断言的是**契约**（"未被纳管的实例应如何处理"），而不是某个实现类的某个字段值。

### 4. 限流后端的一致性语义

| 场景 | 行为 |
|---|---|
| Redis 可用 | 原子脚本执行（Lua），单次判定、无读改写竞态 |
| Redis 不可用 | 启用本地降级窗口：**有明确额度上限、有明确 TTL** |
| 本地窗口耗尽 | 拒绝请求（不放行） |

本地降级窗口存在的意义是避免"Redis 故障 = 完全不限流"（在来源项目里这正是默认行为，会导致下游被冲垮）。
但它必须有上限与过期时间，不能变成一块永久的免检额度。

### 5. 熔断状态使用无锁更新

保留 `LockFreeCircuitBreaker` 的思路（这部分来源项目做得对）：状态向量用 `AtomicReference` + CAS 更新，
并携带版本号防止 ABA —— 窗口期被计数清零又恢复的场景会让纯 CAS 判断误判为状态未变。

### 6. 热路径必须有索引

`service_config` / `service_instance` 及其外键列必须建索引。
索引的取舍标准是**查询路径**而不是表的大小：日志表大但查询少，
配置表小却在每次请求路径上被读取，后者才是需要索引的。

### 7. 配额结算的唯一入口

配额的扣减与结算由同一处驱动（消费 `Outcome`），并且是**幂等**的：
同一 `requestId` 重复结算不应产生第二次扣减。这让重试与网络抖动不至于重复计费。

## 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 保持 fail-open，靠配置规避 | fail-open 是默认值而非配置问题；只要默认是"健康"，任何遗漏都会静默变成放行 |
| Redis 故障时直接放行 | 那就是在最危险的时候（依赖已故障）撤掉保护 |
| Redis 故障时完全拒绝 | 比放行安全，但会把 Redis 的单点故障放大成全站不可用；本地降级窗口是中间解 |
| 用 synchronized 保护熔断状态 | 治理状态在请求热路径上，锁竞争会直接影响吞吐；无锁方案已验证可行 |
| 每个治理组件各自订阅上游事件自行判断 | 回到 0006 的根因：各自观测各自的结果，口径必然发散 |

## 后果

**正面**

- 熔断器、限流、健康检查共享同一个结果来源，"同一个请求在 A 组件看来成功、在 B 组件看来失败"不再可能
- fail-closed 让配置遗漏在第一次请求时就暴露，而不是潜伏到流量高峰
- 本地降级窗口把"Redis 故障"从一个全有全无的事件变成一个可度量的降级

**负面**

- fail-closed 会**降低容错外观**：配置缺失时服务表现为不可用而非"勉强能用"。这是刻意选择的
- 本地降级窗口引入了第二套额度语义，运维上需要理解"本地额度"与"远端额度"的关系
- 索引与结算幂等增加了实现负担，但这些是必要成本

## 如何验证

- [ ] 未纳入健康管理的实例不接收流量（负向测试：故意漏配一项健康检查）
- [ ] Redis 不可用时进入本地降级窗口，且窗口有额度上限与 TTL；额度耗尽后拒绝
- [ ] 同一 `requestId` 重复结算只扣一次
- [ ] `service_config` / `service_instance` 的外键与常用查询列上存在索引（可由迁移脚本静态检查）
- [ ] 没有任何治理组件在 `OutcomeObserver` 之外获取成功/失败（依赖方向扫描）
