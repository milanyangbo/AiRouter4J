# 流式的契约用例（SSE）

与 `contract/`（非流式，比响应 JSON）平行，这里比的是**帧序列**。

## 目录怎么被发现

一个用例一个目录，放入 `upstream.json` + `expected.json` 即被自动发现，**不需要改测试代码**。

## 两个文件的形状

`upstream.json`：

```json
{
  "status": 200,
  "chunks": ["data: {...}\n\n", "data: [DONE]\n\n"]
}
```

`chunks` 里每一块都是**原始字节的角度**：想让一个多字节字符被劈开，就把它的两个字节分别
放进相邻的两块。录制器按块写出，块间不留静默（这里要的是确定性的字节序列，不是时序）。

`expected.json`：

```json
{"frames": ["{\"id\":\"...\"}", "[DONE]"]}
```

`frames` 是客户端会收到的 `data:` 载荷序列，**按顺序**。比对是语义级的（解析后比对树），
不断言键顺序；`[DONE]` 不是 JSON，按原文比。

## 为什么哨兵本身要被断言

`[DONE]` 的存废是一个**被断言的事实**，不是一个默认动作。它出现在基线里，意味着
「这一版会不会发哨兵」的任何改动都会在这里红，而不是在客户端那边表现为「流不结束了」。

## 现有用例

| 目录 | 守什么 |
|---|---|
| `basic/` | 开场 → 内容 → 终态 → 哨兵，顺序与 `created` 透传 |
| `usage/` | 用量单独成帧，厂商明细（`vendor_cache_hit`）原样回到客户端 |
| `keepalive/` | 注释与空 `data:` 帧不产生客户端帧，也不冒充终态 |
| `frame-after-sentinel/` | 哨兵之后的帧不出现在客户端（终态是最后一个事件） |
