# ADR-0013: 配置模型与运行时注册表

- **状态**：已接受（新增，2026-10-25）
- **日期**：2026-10-25
- **相关**：[0001 目标态](./0001-project-scope-and-lineage.md)、[0003 模块结构](./0003-module-structure-and-dependency-direction.md)（`registry` / `select` 包）、[0007 治理模型](./0007-traffic-governance-model.md)（实例维度与选择链）、[0009 形态自述](./0009-second-wire-shape-and-shape-self-description.md)、[0012 存储](./0012-storage-migrations-and-cluster.md)

## 背景

九类能力里有六类——负载均衡、规则路由、失败转移、限流作用域、配额维度、控制台的实例管理——
全部以「一个服务下挂多个实例」为前提。来源项目有这个模型（`service_config` / `service_instance`），
但它是**配置表**而不是**运行时对象**：配置被读成散落的属性，实例的选择过程散在若干 handler 里，
于是「这个实例此刻能不能被选中」没有一个可回答的位置。

当前本项目的状态是配置里只有一个地址（`EndpointProperties`），没有服务、没有实例集合、没有选择过程。
**缺的不是配置格式，是一个维度。**

第二个背景是「加一家厂商」的成本。来源项目为 9 家各写一对 transformer（110 个相关文件），
其中 vLLM / GPUStack / Xinference / LocalAI 的形状完全一致 —— 差异只是默认地址与少数字段名。

## 决策

### 1. 三级配置模型

```text
Service（逻辑服务名，客户端可见）
  └── ModelInstance（实例）
        ├── id
        ├── Endpoint（baseUrl / 凭证 / 超时）
        ├── UpstreamShape（形态：说哪一种话）
        ├── weight（权重）
        └── enabled（启用标志）
```

形态决定「地址该长什么样」「要不要凭证」（[0009](./0009-second-wire-shape-and-shape-self-description.md)）；
实例决定「打到哪里」。**同一服务下的实例可以有不同的形态。**

### 2. 加一家 OpenAI 兼容厂商是一份配置，不是一个类

形态相同时，新增厂商 = 新增一个实例配置（地址 + 形态 + 权重）。需要写代码的只有 wire 形态
真的不同的那几家（Anthropic Messages、Gemini `generateContent`）。

这条是 [0009](./0009-second-wire-shape-and-shape-self-description.md) 第 5 节在配置层的落地：
对齐的是**形态覆盖**，不是适配器数量。

### 3. 完整性校验在启动期判红

| 校验 | 时机 | 失败行为 |
|---|---|---|
| 形态取值未知 | 启动期 | 抛异常，不回落默认（[0009](./0009-second-wire-shape-and-shape-self-description.md) 第 1 节） |
| 地址与形态不匹配（`/v1` vs `/api`） | 启动期 | 判红，报错写成人话 |
| 形态需要凭证但没有 | 启动期 | 判红 |
| 实例未纳入健康管理 | 运行期 | **不可用**（fail-closed，[0007](./0007-traffic-governance-model.md) 第 4 节） |

启动期判红的理由：配错的后果是每一次调用都打在错误的协议上，
而「打错了还一直在打」比「起不来」难查得多。

### 4. 配置来源可追溯

配置可以来自多个来源（yml / 环境变量 / 数据库）。**必须能回答「这个键的值是从哪来的」**——
来源项目在这里的表现是同一个默认值在两个方法里各写一遍且取值不一致，
排查时只能靠读代码猜。

实现要求：任一配置项都能给出「来源 + 是否被覆盖 + 最终生效值」。

### 5. 注册表：配置 → 运行时对象

`registry` 持有服务与实例的运行时对象（含熔断状态、延迟样本、健康登记）。
配置的每次变更产生一个新版本（[0012](./0012-storage-migrations-and-cluster.md) 第 7 节）。

**热重载不重建整个上下文。** 重建会丢掉三样东西：在途的流、熔断器的计数、延迟样本。
丢掉它们意味着一次配置变更等于一次全站状态清零 —— 那不是热重载，是重启。

热重载的正确粒度是**替换注册表里的对象**，并让在途请求继续用它们开始时拿到的那一份。

### 6. 凭据只从环境变量来

`Endpoint` 的 baseUrl 与凭证只从环境变量读取，配置文件里只能是占位符，
**任何受跟踪文件中都不出现真实凭证**。凭证只在形态需要它时才必填。

### 7. 多副本下配置变更走事件广播

配置变更经 Redis 广播同步到各副本（[0012](./0012-storage-migrations-and-cluster.md) 第 6 节）。
广播的是「变更事件 + 版本号」，不是全量配置 —— 全量推送是来源项目 `HttpConfigPushService`
的形状（向一个并不存在的端点推全量配置），不搬。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 每个厂商一个适配器类 | 形态相同的差异只是默认地址与字段名；由配置承担（[0009](./0009-second-wire-shape-and-shape-self-description.md)） |
| 配置直接读成散落属性（来源项目的形状） | 「这个实例此刻能不能被选中」没有可回答的位置；选择过程会散进若干 handler |
| 形态校验放在调用时 | 打错了还一直在打，比起不来难查 |
| 未知形态回落默认 | 同上 |
| 热重载重建 ApplicationContext | 丢在途流、熔断计数、延迟样本；一次配置变更等于全站状态清零 |
| 广播全量配置 | 来源项目 `HttpConfigPushService` 的形状，目标端点并不存在 |
| 允许配置文件里写真实凭证 | 泄露路径太多；且会让「配置能不能提交」变成一个需要人盯着的判断 |
| 同一服务下强制同形态 | 真实场景里同一逻辑服务会挂不同形态的实例（自建 + 云端） |

## 后果

**正面**

- 九类能力有了共同的前提数据结构，作用域标识（`service` / `instance` / `client`）第一次成立
- 加厂商的成本从「写两个类 + 发版」降到「加一份配置」
- 完整性在启动期判红，配置漏项表现为不可用而不是静默放行

**负面与风险**

- 多一层间接：请求路径上要先查注册表的运行时对象。要确认这一步的成本（Phase A 出口时测）
- **热重载的粒度是本 ADR 最容易做错的地方**：替换对象与重建上下文之间的界限要靠测试钉住，
  而不是靠实现者自觉
- 「配置来源可追溯」需要额外的数据结构与展示手段，它是为可排查性付的成本
- 实例可跨形态带来一个后果：同一服务下的实例在凭证要求上可以不同，
  配置校验要按实例而不是按服务判

## 如何验证

- [ ] 一个服务可挂多个实例，且实例可以是不同形态
- [ ] 加一家 OpenAI 兼容厂商只改配置、不改代码
- [ ] 形态未知 / 地址不匹配 / 缺凭证在**启动期**判红，不回落默认
- [ ] 任一配置项能回答「来源 + 是否被覆盖 + 最终生效值」
- [ ] 热重载不重建上下文：在途流、熔断计数、延迟样本在重载后仍然存在（有测试）
- [ ] 配置变更产生新版本；多副本下经事件广播同步（广播的是事件 + 版本号，不是全量）
- [ ] 未纳入健康管理的实例不可用（fail-closed，与 [0007](./0007-traffic-governance-model.md) 一致）
- [ ] 受跟踪文件中不存在真实凭证（有测试）
