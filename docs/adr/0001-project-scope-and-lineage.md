# ADR-0001: 项目定位、血统与二开边界

- **状态**：已接受
- **日期**：2026-10-23
- **相关**：[0002 技术栈](./0002-tech-stack-and-version-pinning.md)、评审记录 [`docs/planning/legacy-review.md`](../planning/legacy-review.md)

## 背景

要的是一个**能用的 AI 网关**。对已有的开源网关做二次开发是实现方式之一，本身不需要额外的正当性论证。

来源项目状况（实测）：

| 项 | 事实 |
|---|---|
| 来源 | `JAiRouter`，License 为 Apache-2.0 |
| 规模 | 主代码 819 个 `.java` / 149,148 行；测试 426 个文件 / 4,266 个 `@Test` |
| 技术栈 | Java 17 + Spring Boot 3.5.5 + WebFlux + JPA + Flyway + Caffeine/Redis |
| 署名痕迹 | 293 处 `@author JAiRouter Team`、19 处 `Copyright 2024 JAiRouter Authors` |
| Git 历史 | 仅 1 次提交，且该提交几乎为空 —— 没有可继承的提交历史 |

没有历史可继承这一点很关键：**它意味着"保留上游提交链条"这个选项根本不存在**，
唯一可选的形态就是把代码作为素材搬运，因此不必为丢失历史而纠结。

## 决策

### 1. 定位为二次开发，坐标独立

`groupId` 改为 `io.github.airouter`，包名由 `org.unreal.modelrouter` 迁往 `io.github.airouter.*`。

不声称整个网关是原创。改动范围内的设计由本项目承担，来源项目的设计与实现仍属于上游作者。

### 2. `legacy/` 是素材库，不是只读档案

来源代码放在 `legacy/` 下，用途有两个：

- **参照**：里面的实现是可以被直接读取、裁剪、改造后进入新代码的
- **对照**：被丢掉的东西要在 `docs/planning/legacy-review.md` 里留下"为什么丢"，避免后来的人又把它加回来

`legacy/` 不参与构建（不在根 pom 的 `<modules>` 里）、不被 CI 扫描。

### 3. 不追求功能对等

不做"把来源项目的每一项能力都复刻一遍"。先通读再分类处理：

| 类别 | 处置 | 例子 |
|---|---|---|
| 实现得对、且当下就需要 | **直接搬过来**，改包名与必要的 API | 限流四算法、LB 策略集、`LockFreeCircuitBreaker`、Flyway 表结构、脱敏规则引擎的规则/引擎分离、前端页面、Docker 与 K8s 编排 |
| 方向对但有实质缺陷 | **改**，并写清楚缺陷是什么 | 流式终态上报（见 [0006](./0006-streaming-terminal-outcome-contract.md)）、SSE 逐帧脱敏、6 包循环依赖、若干上帝类 |
| 来源项目没有、而本项目需要 | **新增** | Agent 层、开启测试的真正集成能力、CI 与门禁 |
| 收益撑不住复杂度 | **删掉** | 4 张配置版本化/审计表及周边 Service、160 个自研 tracing 类、向不存在端点推送全量配置的 `HttpConfigPushService`、遮蔽 `/actuator/metrics` 的自研 Controller |

### 4. 保留署名

上游是 Apache-2.0。搬运进来的文件保留原有的 `@author` 与版权头；README 顶部写明来源仓库、原作者与 License。删除署名不是"二开"的必要条件，反而会引入合规问题。

## 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 全面重写到与来源项目功能对等 | 大量工程预算会消耗在对齐细节上（K8s 编排、20 张表的迁移兼容性），而这些地方的改动并不能让网关本身变好 |
| 只做外层包装，内部机制不动 | 来源项目最严重的问题正在内部机制里（流式结果上报、脱敏路径），包一层外壳修不掉 |
| 抹去来源痕迹、当作完全自有作品呈现 | Apache-2.0 要求保留署名；且代码里 293 处署名痕迹客观存在，声称原创经不起核对 |

## 后果

**正面**

- 起点不是空白：Flyway 表结构、限流算法、熔断实现、LB 策略、前端页面与部署编排都可直接取用
- 重构范围可控：可以一次一个域推进（先把路由链路打通，再动治理层）

**负面**

- `legacy/` 长期存在，需要一个明确约定防止它被误当作可维护代码 —— 该约定写在根目录 `AGENTS.md` 里
- 搬运进来的代码质量参差，评审时容易陷入"要不要顺便改一改"；需要按 ADR-0008 的测试约定先锁行为，再动结构
- 搬代码时要同时处理包名迁移与 Boot 4 API 变更（见 [0002](./0002-tech-stack-and-version-pinning.md)），两类变更混在一起会增加单次变更的审阅负担

## 如何验证

- [ ] `legacy/` 不在根 pom 的 `<modules>` 里，且 CI 不扫描该目录
- [ ] README 顶部写明来源仓库、原作者、License 与二次开发声明
- [ ] `docs/planning/legacy-review.md` 对每一条被删除的能力都给出了删除理由
- [ ] 搬运进来的文件保留原有 `@author` 与版权头
