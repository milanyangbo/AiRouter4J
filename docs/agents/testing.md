# 单元测试：什么是好测试，什么不是

测试守的是**坏掉后不会立刻有人发现的规则**；穿透够深，覆盖率自然上来。
文中代码是形状示意，不指代任何文件。

## 一、以"功能"为单位，不以"类"为单位

**错的**：一个类配一份测试，只看得见刚写完的三十行。
**对的**：一个功能写完写一份。**一个功能 = 一份测试，不是一类一份。**

功能怎么算：**能不能单独回答"这条业务流程走通了吗"**——删了产品少一个能力，只换内部实现能力不变。

- 是功能：一个能力包（入口 + 规则 + 落地）。"业务数据查询"含工具、守卫、只读取数，缺一问不出数。
- 不是功能：值对象、工具类、配置类、纯转发的入口——规则归用到它的功能测；没人用的工具类该删。

每个方法从**功能自己的入口**进去，断言**末端结果**——红了（测试失败）看得见断在哪，五条各测一类的给不了。

**入口不是"最外层那个"。** 从系统边界进，验的多半是协议与绑定；功能测试从责任开始的那一层进就够。
接口级契约（状态码、请求头、分帧）是验收的活，不进回归。见判据二。

## 二、组织与界限

| 维度 | 界限 |
|---|---|
| 每模块测试文件 | **10 个以内**（代码量确实大，最多 20） |
| 每文件测试方法 | **最多 20 个** |
| 行覆盖率 | **不低于 60%** |

上限管"散"、下限管"漏"：超了还在按类写，破了是整块没穿到。两头都不是目标——没超别凑数，到了别往上凑。

划完先数：文件顶到上限 = 切细了，合并同一入口下的子能力；一个功能要写 20 条以上 = 切粗了，
按"能否单独回答一条业务问题"再切；仍超就删被深测试顺带覆盖的浅条。

前提可能不同（真库 / 真模型）：**取最重的，整类一起跑**，别按前提拆文件——拆了就回到按类写。

覆盖率破了去补那条链路，不是补 getter 的断言。三个数进脚本，超上限、破下限直接红；统计排除生成代码与配置类。

## 三、写之前先 review 代码，别急着写断言

看到方法就写断言，是按类写。开工顺序：**列模块对外入口 → 每个入口所属的能力包算一个功能 → 逐个画链路
→ 全部画完再统一排序 → 最后动手写。** 每个功能走这四步：

1. **画出主链路**：入口、经过哪些环节、落在哪。写下来，不是想一下。
2. **列出守的规则**：写错系统照样跑、日志干净、只有结果不对的那些。
3. **按穿透度排序**（见五·④）：穿得深的优先，只碰一层的排后面。
4. **在末端断言**：断言结果，不断言私有方法返回值。

链路画不出来 = 这功能耦合得没法测，先改代码。

## 四、为什么"文件少"和"覆盖多"能同时成立

一条从真实入口进去的测试，走通的是整条路（以对话请求为例）：

```
reply(问题) → 分流 → 鉴权 → 工具循环 → SQL 守卫 → 真库
```

**看层数和入口，不看环节叫什么。** 它绿了，证的不是"鉴权对、守卫对、事务对"各自成立，
而是"越权在工具执行前被拦下、拦下后事务没开"。十条各测一个正则，碰不到存储层。

**覆盖量来自路径长度，不是条数**——每条只碰一个类，覆盖同样多就得写同样多条。

## 五、四条判据

### 判据一：这条规则坏了，会不会立刻有人知道？

| 坏掉之后 | 例子 | 要不要写 |
|---|---|---|
| 编译不过 | 改了方法签名 | 不写——编译器就是测试 |
| 启动就炸 | 缺 bean、缺 key | 不写——启动失败比断言更响 |
| 当场异常 | 传 null、空字符串 | 不写——调用处立刻看到 |
| **照样跑，只是结果不对** | 工具静默消失、数据落到默认 schema、越权放行、参数被 shell 解释 | **必须写** |

**一处必须分清。** "启动就炸"指框架抛的（缺 bean、缺 key），写断言只是复述框架的话。
我们自己那句校验必须测：删了系统照样启动，只是悄悄退化成默认。"配了目录不存在 → 启动失败"同理，
守的是**这个失败是我们主动设的**。

### 判据二：测的是机制契约、自身功能、模型可用性，还是装配？

**入口选在责任的边界上，不在系统的边界上。** 协议、绑定、容器是委托出去的，从那里断言验的是别人的正确性；
**我们的判断从哪一行开始生效，测试就从哪一行进去。**

```java
// 反例：从系统边界进。它红了十次，八次是端口、序列化、构建配置——与要守的规则无关。
mockMvc.perform(post("/orders").content(越权的请求))
        .andExpect(status().isUnauthorized());

// 正例：同一条规则，从判断生效的那一行进，断言业务结论。
assertThatThrownBy(() -> orders.place(guest, order))
        .isInstanceOf(AuthorizationException.class);
```

**例外只有一种**：内层拿替身顶掉了真实接缝，而接缝自己也会坏——装配、序列化、事务边界、SQL 本身。

```java
// 模块级这条是绿的，但鉴权 Advisor 是测试自己挂进链的：它验的是"判断对不对"。
ChatClient.builder(model).defaultAdvisors(new AuthzAdvisor(registry)).build();
assertThat(agent.reply(guest, "上周华东区成交额")).doesNotContain("128400");

// 启动类哪天漏了 new AuthzAdvisor(...)，上面那条照样绿——"挂上没挂上"只能从外层进，
// 而它只值一条断言，不把判断本身再验一遍。
assertThat(http.ask(guest, "上周华东区成交额")).doesNotContain("128400");
```

**适配层自己的规则照样要测**，只是对着那个类测，不必起容器——它同样是"照跑、日志干净、结果错"。

```java
// 适配层里的判断（不是框架的）：头读不出来就必须"认不出人"。
// 写歪成 orElse(GUEST) 的话，请求照常 200、日志干净，只是每次都拿着别人的身份去查库。
static Optional<Principal> identify(String userHeader) {
    return (userHeader == null || userHeader.isBlank())
            ? Optional.empty() : Optional.of(Principal.of(userHeader));
}

assertThat(identify(null)).isEmpty();
assertThat(identify("   ")).isEmpty();      // 空白不是"省略"，是缺失
assertThat(identify("ethan")).isPresent();
```

**同一功能可以测多处，但四类对象不同，别混：**

| 类别 | 测什么 | 真模型 | 典型内容 |
|---|---|---|---|
| 功能内 · 机制契约 | 连接怎么建立、会话丢了是重连还是重试、清单为空为什么必须直接失败 | 不要 | 生命周期与状态迁移 |
| 功能内 · **自身功能** | 这个能力自己的业务逻辑对不对 | 不要 | SQL 守卫与只读执行；MCP 的"参数 → 命令 → 结果" |
| 模型可用性 | 模型会不会选对这个工具、能不能把自然语言变成对的调用 | 要 | 一句话进 → 一轮工具调用 → 一整段出 |
| **跨模块装配** | bean 接没接上、工具清单里有没有它、迁移跑没跑 | 不要 | 一条冒烟，从最外层进一次，只断言"接上了" |

**"功能内只测契约"是错的。** 业务工具、MCP 的参数翻译都是我们的逻辑，翻错成命令参数，连接再稳也问不出数。
契约和功能都测，只是**都不用模型**；"模型能不能用起来"归另一层。要防两类事故：一类没人测，或两类测同一件事。

**装配只在"装配本身是风险"时才写**：模块边界多、靠自动配置装配、配置在启动时才生效。别借装配的名义烧 token。

### 判据三：换一种等价实现，这条测试要不要改？

要改，说明它钉的是实现细节，不是行为。

```java
// 反例：把实现抄了一遍。有人把上限从 30s 改成 20s（合法改动），测试跟着改，
// 于是"改测试"变成了"让红灯变绿"的动作，测试失去了独立判断。
assertThat(policy.maxTimeoutMillis()).isEqualTo(30_000);

// 正例：钉行为。上限具体是多少不重要，"超过上限就拒绝、且不夹取"才重要。
assertThatThrownBy(() -> policy.requireTimeoutWithinCap(60_000))
        .isInstanceOf(PolicyViolationException.class)
        .hasMessageContaining("超过上限");
```

自查：换掉实现、行为不变，这条测试会失败吗？会 = 钉错对象。

### 判据四：它穿过了多少核心逻辑？

决定**先写哪个**：两条都该写时，先写穿得多、被多个入口共用的。

| 入口 | 穿过的逻辑 | 一条测试的收益 |
|---|---|---|
| 一次业务查询 | 规则守卫 → 只读事务 → 行数上限 → 结果映射 | 高：几个环节一次走完 |
| 一次鉴权判定 | 登记表查询 → 未登记即拒绝 → 只读不可写 | 高：鉴权链的判定核心 |
| 一次标识拼接 | 一次字符串拼接 | 低，但它防"悄悄落到默认位置"，仍要写 |

先写深的，浅的常被顺带覆盖——"文件少而覆盖全"就是这么来的（见四）。纯函数验过的规则，
进程里还得再验一次落地（见六·3）。入口写成"某个类的某个方法"，不写"某文件的第几行"——红灯时才能顺链路走完。

## 六、好测试长什么样

**1. 钉反直觉的那一侧**

```java
// "普通 select 放行"谁都会写，坏了端到端立刻抓到。值钱的是这条：
// 字符串层面看有分号，数据库层面它是一条语句。不先去注释就会误拒。
@DisplayName("注释里的分号不构成多语句")
assertThat(rejectionOf("select 1 from t -- ; drop table t")).isEmpty();

// PostgreSQL 允许 with 里做 delete 再 returning 出来。
// 任何"首关键字是 select 或 with 就放行"的规则都会放过它。
@DisplayName("可写 CTE 会被拦下：with 开头不等于只读")
assertThat(rejectionOf("with d as (delete from t returning *) select * from d")).contains("delete");
```

一条防误拒、一条防漏放，只有输入长这样才暴露；不专门写就永远不红。

**2. 钉静默失效**

```java
// 缺陷姿势是"工具静默消失"：不报错、不告警，只是模型手上没有那个工具，
// 于是它开始编答案。表现是"模型变笨了"，没有一行日志指向原因。
@DisplayName("第二个工具来源进来时，第一个来源的工具仍在")
assertThat(toolNames(context)).contains("原有工具", "新来源的工具");
```

同类：目录不存在就启动失败、定义写坏就整层起不来、标识空串直接拒绝。
共性是**代码照跑、日志干净、结果错**，判据一里最贵的一格。

**3. 同一组约束要验两遍：规则写对了，还要真落到进程上**

```java
// 纯函数：约束本身对不对（指向目录外的符号链接被挡住）
assertThatThrownBy(() -> policy.resolveInside(root, "leak.txt"))
        .isInstanceOf(PolicyViolationException.class).hasMessageContaining("符号链接");

// 起真进程：约束有没有真的落到进程上（工作目录锁在包目录内）
assertThat(Path.of(outcome.stdout().strip()).toRealPath()).isEqualTo(pkg.root().toRealPath());
```

前一条红 = 约束没写，后一条红 = 写了没接到进程上。假执行器只验得到"调没调用"，验不到"进程起在哪儿"。
**这不是重复，是测试必须穿到落地。**

两遍只用在**约束必须落到外部**的地方（库、进程、文件、网络）；纯内存里的规则，纯函数验过就够，别再起一遍。

## 七、坏测试长什么样

| 坏在哪 | 形状 | 该换成什么 |
|---|---|---|
| 测框架 | `client.prompt("x").contains("x")` | 守"流式被降级成一次性返回"这种我们接错装配才会出的事 |
| 测入口绑定 | 只断言状态码、只断言响应体被序列化成 JSON | 挪进验收（curl / Postman）；非留不可就守"没身份就进不到业务层" |
| 测配置透传 | `assertThat(model.getOptions().getModel()).isEqualTo(config)` | 守"温度归零两次答案相同"，证明配置真的生效了 |
| 抄实现 | `assertThat(sessionIdOf(u)).isEqualTo(PREFIX + u)` | 守"身份为空就拒绝"，那是静默且会串号的真规则 |
| 按类配一份 | 一个类一份文件，各测一个正则 | 改成这个功能那一份，从入口穿过去 |
| 参数化压语义 | 不同原因的错误塞进一张 CSV | 报错只剩"第 N 组"，方法名里的信息全丢 |

参数化只有一句判据：**这几行红了，是同一个原因、修同一处代码吗？** 是 → 可以；不是 → 各写一条。

坏测试多半**浅**——只碰一个类、走不出一层。但**浅不等于坏**：只碰一层却守静默失效的（空值、越权、边界值）照样要写，
裁判是判据一，不是深浅。深的测试覆盖到的地方不必再写一条。

还有一类只能实测发现：**断言了不存在的现象**。流式响应逐块发出后，后置处理改不到已发出的块，
"响应里有标记"于是恒红——改成"后置处理被调到了几次"。每条路径先跑一遍，再写断言。
