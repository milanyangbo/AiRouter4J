## 背景

P0 十张票交付的是一个**切片**：一个 Face（OpenAI 兼容）、两种 Provider 形态（OpenAI 兼容 /
Ollama 原生）、单实例、熔断与结算闭环、契约测试与结构规则。它证明了架构骨架能立住，
但网关应有的绝大部分功能还不存在。

对照 `legacy/README-ZH.md` 的能力清单，九类功能里我们只覆盖了「韧性」的一小部分：

| legacy 能力 | 我们此刻的状态 |
|---|---|
| 适配器（9 个内置 + 任意 OpenAI 兼容厂商） | 2 种形态，且只能配一个端点 |
| 负载均衡（7 种策略） | 不存在——只有一个实例，没有「选」这件事 |
| 规则引擎（条件路由 + 命中统计） | 不存在 |
| 韧性（熔断 / 失败转移 / 限流 / 缓存） | 熔断与可用性闸门已有；失败转移、限流、缓存都没有 |
| 配额（多维多窗口账本） | 不存在 |
| 记录治理（调用历史三档） | 不存在 |
| 可观测性（指标 / 链路 / 慢查询 / 告警） | 只有健康端点与在途计数 |
| 持久化（H2 / PG + Flyway） | 不存在 |
| 多副本（事件广播 / 共享计数 / 分布式锁） | 不存在 |
| 控制台（`/admin/` 73 页） | 不存在 |

**差距的本质不是「缺九个模块」，而是缺一个维度。** 上表里除了适配器与记录治理，
其余六类——负载均衡、规则路由、失败转移、限流作用域、配额维度、控制台的实例管理——
全部以「服务 → 多个实例」为前提。我们此刻的实例是配置里的一个地址，
没有标识、没有集合、没有选择过程。在这个前提下先做限流，
等于把限流的作用域硬编码成「全局一个桶」——那不是限流，是一个全局开关。

## 决策

### 1. 先建实例维度，再铺功能

Phase A 的三张票全部服务于一件事：让「一个请求进来 → 选中一个实例」这条链真的存在，
并且链上的每一环都能被单独断言。之后每一类功能都是往这条链上加一节，
而不是各自发明一条自己的链。

这也是为什么 Phase A 不是限流：限流的作用域是 `service / instance / client`，
而这三个标识 presently 都不存在。

### 2. 存储一次到位，但 DB 与 Redis 都必须可以缺席

按决定一次到位：默认 H2，`DATABASE_URL` 指向 PostgreSQL 时切 PG（配 Flyway，两种方言各一份迁移）；
Redis 承载共享状态（限流 / 配额计数、跨副本事件、分布式锁）。

**「一次到位」不等于「强依赖」。** 两者缺席时系统必须继续工作，且这不是兜底，是契约：

- Redis 缺席 → 计数走本地后端、事件总线退化成本地、锁退化成单机无锁，**启动日志明确说明降级生效**
- DB 缺席或不可用 → 运行时配置回落到内存 store
- 缺席路径本身是**必测行为**（不是「测试环境没有 Redis 就跳过」）

本机已经跑着 Redis 7（`:6379`）与 PG 16 + pgvector（`:5432`），
因此集成测试打的是真实存储，不是桩。被否决的「先内存、后置存储」方案会把
「Redis 挂了怎么办」这个问题无限期推迟——而那恰恰是 legacy 里写得最好的一部分
（`usageStrict`：**读不到用量绝不当 0**，否则会凭空错杀请求）。

### 3. 不新增模块，gateway 内新增包；core 保持零依赖

新阶段新增的包全部落在 `airouter-gateway`：

| 包 | 职责 |
|---|---|
| `config` | 运行时配置模型：服务 / 实例 / 适配器 / 规则 / 网关策略 |
| `registry` | 配置 → 运行时对象的注册表，热重载与版本 |
| `select` | 实例选择：负载均衡策略与选择链 |
| `store` | 持久化：JPA / Flyway，配置版本与调用历史 |
| `cluster` | 多副本：事件广播、共享计数、分布式锁 |
| `admin` | 管理面 API |

不新增模块的理由：新增一个模块要配第四套依赖闸门与结构规则，
而 `gateway` 已经是「知道 Spring、知道基础设施」的那一层。
代价是结构规则要随之扩展——每个新包都要写清它知道什么、不该知道什么，
尤其 `store` 与 `cluster` 不该认识 wire 形态，`select` 不该认识 HTTP。

### 4. 适配器延续「形态自述」，vLLM / GPUStack / Xinference / LocalAI 不是四个适配器

legacy 的 62 个适配器文件（13.2k 行）里，真正不同的只有三种形态：
Ollama 原生、Gemini 原生、Claude 原生。vLLM / GPUStack / Xinference / LocalAI / normal
各自有一对 `XxxRequestTransformer` / `XxxResponseTransformer`（合计约 3.5k 行），
形状完全一致——差异只是默认地址、路径与少数字段名。

我们已有的 `UpstreamShape`（`openai-compatible` / `ollama`）正是为此而设：
新增一家 OpenAI 兼容厂商是**一份配置**，不是一个类。
需要写代码的只有 wire 形态真的不同的那几家（Anthropic Messages、Gemini generateContent）。

### 5. 限流与配额合成一个内核，而不是两套

legacy 有两套限流且零共享代码：业务面 `router/ratelimit`（2.4k 行，三级作用域 + 5 种算法）
与管理面 `AdminApiRateLimiter`（一个 WebFilter，手写分钟/小时计数器）。
重写时是一个内核 + 两条入口：一个「判定接口」配多个作用域（global / service / instance /
client），后端分 Redis 与本地两级，Redis 不可用时降级到本地并记指标。

### 6. RBAC：先把 legacy 的权限面分类记录下来，重点实现，逐步对齐

legacy 有 63 个权限码、83 条 URL 规则、4 个角色模板，且双轨（URL 矩阵 + `@PreAuthorize`），
其中 WebFlux 下类级 `@PreAuthorize` 实际不可靠（它自己的注释承认，靠 URL 规则兜底）。

我们不一次铺满 63 个码，而是：先把 legacy 的全部权限项**抄录并分类**（读 / 写 / 管理、
按域分组）作为待办台账，第一阶段只实现「管理面需要的那几个」并保留 URL 矩阵这一条轨，
其余按阶段接。有一条必须在第一版就钉住：**网关凭据（`X-API-Key`）绝不透传给下游**
——legacy 靠结构与文档保证，**没有测试**，这正是重写要补的那一类断言。

### 7. 控制台放到最后，且是「适配 legacy 前端」而不是重写

`legacy/frontend` 是 73 个页面 / 5.1 万行 / 86 个 i18n / 414 个 E2E，是全项目最贵的资产，
重做性价比最低。前置条件是：管理面 API 的契约先稳定并被契约测试钉住，
之后把前端接上来（换 api 层与少量字段），而不是从头写页面。
在此之前，「配置能不能改」由管理 API 与测试回答，不由界面回答。

### 8. 可观测性只出指标与结构化日志

与 legacy 一致：告警出口限定为 Prometheus 指标 + 结构化日志，仓内**不实现**任何推送通道
（邮件 / Webhook / IM），接入放在 Alertmanager 或日志平台。这条要写成结构规则级别的可断言约束，
否则「顺手加一个 Webhook」会在某个时刻发生。

### 9. 不搬运 legacy 代码；运维资产直接搬

- **可搬**：Grafana 面板 JSON、Prometheus / Alertmanager 规则、Loki / Promtail / Tempo 配置、
  K8s 清单与 compose、以及 `scripts/audit/` 那类审计脚本的思路（配置键消费方对账、
  前后端接口对账、错误码注册表对账）
- **不搬**：6 个重复的 OpenAI 兼容 transformer、4 套并存的 store + 4 层 tier、
  4 套版本服务、自研 metrics 采集与 tracing context（Spring Boot 4 + Micrometer / OTel starter 下几乎全部可省）

## 阶段与票

先广度后深度：Phase B 把九类各铺一层（每类都能用、都有测试），
Phase C 再回头把核心链路做深。

### Phase A —— 地基：让「选一个实例」这件事存在

| 票 | 标题 | 依赖 | 验收要点 |
|---|---|---|---|
| 11 | 存储与迁移：H2 默认 / PG 按 `DATABASE_URL`，Flyway 双方言 | — | 两种库都能启动；迁移幂等；**存储缺席时降级并明确记录** |
| 12 | 服务 / 实例 / 适配器配置模型与运行时注册表 | 11 | 配置完整性校验在启动期判红；配置来源可追溯；热重载不重建整个上下文 |
| 13 | 实例选择：轮询 / 加权 / 随机 + 选择链 | 12 | 多实例端到端；选择与「健康 / 熔断 / 限流」的顺序被断言 |

## 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 先做限流 | 作用域（service / instance / client）此刻不存在，做出来是全局开关而非限流 |
| 先内存、后置存储 | 存储接入时要回头改所有写入方；且「Redis 挂了怎么办」这一必测行为会被无限期推迟 |
| 新增独立模块放存储与集群 | 第四套依赖闸门与结构规则的成本大于收益；`gateway` 已是基础设施层 |
| 照搬 legacy 的 6 个 OpenAI 兼容适配器 | 约 3.5k 行的重复，差异只在默认地址与字段名；由配置承担 |
| 重写控制台 | 5.1 万行、414 个 E2E，是最贵且最不该先做的资产 |
| 一次性铺满 63 个权限码 | 变成配置搬运；先分类、后按需接，并把「凭据不透传」这类真断言先钉住 |

## 后果

**正向**

- 每类功能都挂在同一条选择链上，作用域与判定顺序只有一处定义
- 存储与降级从第一天就是契约而不是补丁——本机有真实 Redis 与 PG，集成测试不靠桩
- 控制台后置，前端接的是已经被契约测试钉住的 API

**成本与风险**

- 结构规则要从 9 条扩到十几条：每个新包都要声明它认识什么。漏写等于规则静默失效，
  因此每加一条规则都要配一个「违规样例会红」的测试
- 存储进入后测试时间会变长；缓解方式是按 gate 分组跑（票 10 已落 `@Tag` 机制）
- Phase B 有 11 张票，存在「铺得很宽但都不深」的风险。Phase C 的存在就是为了兜住这一点，
  它必须在 Phase B 结束后立刻排期，而不是无限延后
- 管理面 API 若在开发过程中反复改形状，控制台接入会被反复打断。因此契约测试先行（票 27 前置）
