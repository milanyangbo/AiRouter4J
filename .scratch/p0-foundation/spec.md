## Problem Statement

这个仓库目前跑不起来，而且跑不起来这件事本身没人知道。

切换到新坐标系之后，项目里没有任何构建产物：没有根构建文件、没有 Maven Wrapper、
没有持续集成、没有一处生效的质量门禁。任何人 clone 下来都无法判断它是否能工作。

紧接着的问题是更严重的那一个：这是一个二次开发项目，下一步要从 `legacy/` 搬运大量
Jackson 2 时期写成的 JSON 处理代码到 Jackson 3 上。而 Jackson 2 → 3 最主要的产物不是编译错误，
是**编译通过但序列化行为变了**的那类静默变更。以仓库目前的状态（来源项目的端到端验证能力接近于零，
见 ADR-0008），这类变更没有任何东西能发现它们 —— 改完与否、改对与否，全凭肉眼。

ADR-0008 已经把结论钉死了：**验证能力必须先于迁移落地**。现在缺的正是这个前提。

## Solution

建立一条从零到「可运行且可验证」的基线，包含两件事：

1. **构建一个不会因为缺少 skip 开关而失效的骨架** —— 模块结构、版本锁、门禁、持续集成、
   Maven Wrapper，每一项都在默认构建路径上真实生效。
2. **打通一条端到端垂直切片** —— 一个请求从 OpenAI 兼容的 Face 进入，经过 `CanonicalRequest`，
   由 Provider 转发到真实模型端点，上游响应被翻译回 `CanonicalStreamEvent` 流，
   再由 Face 编码成 SSE 返回。同步与流式两条路径都要通。

这条切片不是为了展示功能，是为了让三件事第一次具备被机器判断的条件：

| 契约 | 来源 |
|---|---|
| 流式失败必须驱动熔断 | ADR-0006 |
| 同一份上游字节只被解析一次（CHUNK_PARSE_COUNT=1） | ADR-0005 |
| 新增 Provider 不需要改动 Face | ADR-0003、ADR-0005 |

做完之后，`./mvnw verify` 一条命令能给出可判断的结果，`java -jar` 能起得来，
一条真实的 chat 请求能从新端点走到真实模型再回来。

## User Stories

### 作为 API 调用方

1. 作为 API 调用方，我想向 `/v1/chat/completions` 发送一条非流式请求并获得 OpenAI 兼容的响应，以便现有的 OpenAI 客户端无需改动即可接入
2. 作为 API 调用方，我想发起流式请求并以 SSE 逐帧收到内容，以便降低首字延迟
3. 作为 API 调用方，我希望流式响应以 `[DONE]` 正常收尾，以便客户端知道何时停止读取
4. 作为 API 调用方，我希望出错时收到形态一致的错误结构并带 `[DONE]` 之前的错误帧，以便我能区分「上游出错」和「连接断了」
5. 作为 API 调用方，我希望请求与响应里的厂商私有字段能被原样透传，以便厂商特有能力不会因为网关的存在而丢失
6. 作为 API 调用方，我想在中途断开连接后不再收到任何帧，以便我不必自己处理残留数据
7. 作为 API 调用方，我希望每次响应都携带可用于排查的请求标识，以便我能把它交给维护者定位问题
8. 作为 API 调用方，我希望 token 用量在被支持的情形下如实返回，以便我做成本核算

### 作为网关维护者

9. 作为网关维护者，我想在只有 JDK 的机器上用 `./mvnw clean verify` 完成一次完整构建，以便不依赖预装的 Maven 版本
10. 作为网关维护者，我希望 checkstyle 与静态分析在默认路径上真实生效，以便代码规范不是一句口号
11. 作为网关维护者，我希望不存在任何全局抑制文件，以便规则违约只能靠改代码解决
12. 作为网关维护者，我希望 `core` 模块的依赖树里不出现 Spring / Jackson / Reactor，以便领域模型是被明确的边界保护着的，而不是靠自觉
13. 作为网关维护者，我想在有人不小心让 `core` 依赖了某个框架时构建直接失败，以便结构性问题在合并前被发现
14. 作为网关维护者，我希望 `@Lazy`、字段注入、`getBean()` 按类型查找这三种写法会导致构建失败，以便装配顺序不会被隐式化
15. 作为网关维护者，我想看到任一流式样本上报的延迟是真实耗时而不是零，以便延迟感知负载均衡能正常工作
16. 作为网关维护者，我希望未纳入健康管理的实例不接收流量，以便配置漏项立刻暴露而不是潜伏到高峰
17. 作为网关维护者，我想确认客户端取消一个请求不会把实例判为故障，以便移动端切后台不会熔断掉健康实例
18. 作为网关维护者，我想确认上游连续失败时熔断器会真的打开，以便「熔断器永不 OPEN」这个来自来源项目的缺陷不会重演
19. 作为网关维护者，我希望没有任何组件可以在 `OutcomeObserver` 之外提交成功或失败，以便结果口径不会出现第二个来源
20. 作为网关维护者，我想让模型端点地址与 API 密钥走环境变量，以便它们不会进入版本库
21. 作为网关维护者，我希望 base-url 缺少 `/v1` 后缀时在启动阶段就报错，以便不要等到第一次调用才碰到 404
22. 作为网关维护者，我希望以最小配置就能在本地启动整套东西，以便在无网络环境下也能开发
23. 作为网关维护者，我想让同步与流式两条路径共用同一条治理与观测管道，以便不会出现一条路径被悄悄遗漏
24. 作为网关维护者，我希望同一份上游字节在一次处理流程中只被 JSON 解析一次，以便 CPU 开销不被重复解析吃掉

### 作为构建流水线

25. 作为构建流水线，我想在每个变更上运行编译与单元测试，以便破坏性改动立刻可见
26. 作为构建流水线，我想运行静态分析与依赖方向校验并把它们作为独立 gate，以便质量问题能被准确定位到类别
27. 作为构建流水线，我希望任何 gate 红了就阻断合并，以便不会有人在红色状态下继续堆叠改动
28. 作为构建流水线，我希望门禁不存在可跳过开关，以便「临时关一下」这种事后很难恢复的操作无法发生

### 作为后续迁移工作

29. 作为接下来要从 `legacy/` 搬运代码的人，我希望先有一份 golden-file 契约测试基础设施，以便我搬运前后可以对比同一份输入的输出
30. 作为接下来要加 Provider 的人，我希望我的改动集中在一个包内且 Face 侧零改动，以便我看得清自己影响的范围

## Implementation Decisions

### 模块划分

沿用 ADR-0003 决定的四个模块，本次全部建立起来（Agent 模块本次只建壳，不含编排逻辑）：

- **`core`** —— 领域模型与端口。无任何框架依赖，一个框架出现在它的依赖树里就是设计倒退
- **`gateway`** —— Face / Provider / transport / routing / governance
- **`agent`** —— Spring AI 层，本次仅建立可被 `app` 装配的最小存在，不实现编排
- **`app`** —— 启动、配置装配、打包

版本统一锁定在根构建文件：Spring Boot 4.1.2、Spring AI BOM 2.0.1、Java 21。
这不是建议搭配（Spring AI 2.0.1 直接依赖 Boot 4.1.1 的 starter），详见 ADR-0002。

### Canonical 与终态

- `CanonicalRequest` 与 `CanonicalStreamEvent` 定义在 `core`，不含 Jackson / Spring 标注
- 流式事件按 GLOSSARY 的概念分层：**Opening / Delta / Terminal / Failed**
- `Terminal` 与 `Failed` 必须由 Provider **显式发出**；禁止依赖 Reactor 的 `onComplete` / `onError` 推断结果
- 超过 IdleTimeout 仍未收到终态时，由框架补发 `Failed`（归类为 `UPSTREAM_TIMEOUT`），保证任何一条流有且只有一个终态
- `Cancellation` 是独立的第三种终态，它影响资源回收与部分指标，但**不判为实例故障**

### 唯一结算点

`OutcomeObserver` 是全链路唯一的结果结算点。熔断器、健康检查、延迟统计、后续阶段的配额，
全部只消费 `Outcome`。任何组件不得自行判断一次调用的成败，不得自己去读 HTTP 状态码。

这一条既是设计约束也是代码约束：它表现为一条依赖方向规则，而不是文档里的一句话。

`Outcome.latency` 一律计算到收到终态为止，这让流式与非流式的延迟具有可比性。

### 配置与凭证

- 模型端点地址与 API 密钥**只从环境变量读取**，不写入任何会进入版本库的文件
- 启动时校验 base-url 形态：缺少 `/v1` 后缀时给出可读错误并阻止启动
- 提供不依赖真实网络的本地配置档位，以便在无网络环境下可开发

### 质量门禁

- checkstyle / 静态分析 / 覆盖率全部在默认构建路径上生效，**不提供 skip 开关，不设抑制文件**
- 来源项目正是在这两点上失效的：dev/prod profile 把所有 skip 设为 true，
  叠加一份对 `.*\.java` 全局抑制 186 行的抑制文件。本项目不重复这个错误
- checkstyle 规则数量保持克制但每条真实生效；规则违约的修法是改代码
- Maven Wrapper 必须提交并保证可用，让只有 JDK 的机器也能构建

### 依赖方向的机器保障

引入依赖方向校验，只写少量核心规则：

- `core` 不得依赖任何框架
- `gateway` 内部包之间的允许引用关系
- 没有模块可以依赖 `app`
- 无人可以在 `OutcomeObserver` 之外提交成败结论
- 代码中不得出现 `@Lazy`、字段注入、`getBean()` 按类型查找

规则数量刻意少。规则越多，越容易出现「加个例外算了」的冲动 ——
来源项目那份 186 行抑制文件就是这条路径的终点。

### 持续集成

至少四个 gate，红线阻断合并：

```text
compile & unit     静态分析    依赖方向 / 结构    集成测试
```

### 给后续迁移预留的对照入口

本次不搬运 `legacy/` 的任何实现代码。但 golden-file 契约测试的基础设施要就位，
并且要留下一个「同一份输入 → 期望输出」的对比入口，供后续搬运前后对照。

## Testing Decisions

### 什么算一个好测试

只断言**外部行为**，不断言实现细节。具体到本项目：

- 好测试回答「一个对象/一次请求表现出了什么行为」
- 坏测试回答「我调用了我以为我会调用的东西」—— 这类断言在重构时必然失效，却从来不报错。
  来源项目 4,266 个 `@Test` 里大量是这种，所以它们保护不了任何东西

由此推论：覆盖率不作为准入门槛。来源项目已经证明高 Mockito 覆盖率与真实验证能力几乎没有相关性。
覆盖率可以报告，不用来卡门。

### Seam 的选择

**唯一的行为 seam：入站 HTTP 边界。**

所有行为测试都通过真实的 HTTP 打进运行中的应用。从这一个 seam 可以同时断言：
响应的 wire format（用 golden-file 对比）、流式事件的终态、同步与流式两条路径、
错误传播形态、请求透传。

选择它的理由是它层次最高，因此**不需要任何内部组件的 mock** —— 而这恰恰是来源项目失败的地方。
理想 seam 数量是一个，这里做到了。

**另加一层结构检查：依赖图。**

这不是第二个行为 seam，是另一类检查。依赖方向被破坏时不会体现在任何行为测试里
（服务照样能起来、请求照样能通），只能从结构上单独看。ADR-0003 与 ADR-0006 的核心约束
（`core` 纯净、`OutcomeObserver` 唯一）属于这类，必须由它来兜。

### 上游使用真实模型端点

本切片的上游是**真实的 OpenAI 兼容模型端点**，不引入假服务。

这带来一个真实收益：能验证与真实厂商的兼容性 —— 真实的响应形态、真实的 SSE 分帧节奏、
真实的 token 用量字段。这些是假服务给不出来的。

**但必须接受它的代价**：故障场景无法做到字节级可控。因此故障注入改用以下手段近似：

| 目标场景 | 注入方式 |
|---|---|
| 上游返回错误 | 指向错误路径 / 错误模型名，让上游返回 4xx |
| 上游不可达 | 指向不存在的主机 |
| 上游超时 | 把 IdleTimeout 阈值调到极小 |
| 客户端取消 | 真实断开连接（可读，且是最贴近生产的一种） |

### 由此产生的验证缺口（必须记录）

「上游发出半个 SSE 帧后突然断开连接」这类**精确到字节的截断场景，在此 seam 下不可构造**。
因此 ADR-0006 的验证是不完整的：能验证「上游报错导致熔断」「超时导致熔断」「取消不熔断」，
但不能验证「流成功开篇后中途静默断开」是否也被正确识别为失败。

选项留给后续：当有人要验证这一类场景时，引入一个能控制字节序列的本地上游，
作为**补充**而非替换 —— 真实端点继续负责兼容性发现的职责。这一条记录在此，
是为了让缺口是已知且可见的，而不是被遗忘的。

> **票 06 补记**：那个本地上游已经有了（`RecordedUpstream` 能控制到字节块一级）。
> 「讲完但不发 `[DONE]`」这一类样本现在造得出来，并已纳入 `contract-stream/` 的基线。
> 缺口因此不再是「不可构造」，剩下的是「上游发到一半突然断」这种精确到字节的截断 ——
> 它同样可构造，只是本票没有为它写用例。

### 契约测试

golden-file 契约测试针对的对象是**对外 wire format**：给定上游字节 → 期望的 SSE 输出。
这是后续 Jackson 3 迁移期间唯一能发现静默行为变更的东西。

同时做一条计数型断言：一次流式处理中对同一份上游字节的 JSON 解析次数为 1（CHUNK_PARSE_COUNT=1）。

### 流式必须用专门的断言方式

对流的断言不能只回答「有没有数据」，要回答：

- 终态恰好出现一次，无论是正常、异常还是超时路径
- 取消路径下 `Terminal` 不出现，且熔断器状态不变
- 延迟数值反映真实耗时，而不是零

## Out of Scope

以下内容明确不在本次范围内：

- **Anthropic Face**。本切片只打通 OpenAI 兼容这一条 Face。按 ADR-0005 的渐进收口约定，Face 侧收口要等真正出现第三个 Face 时才做
- **多实例与负载均衡算法**。本切片针对单个已配置实例，不涉及实例选择策略
- **限流的完整维度与参数调优**。本次只保证「结果结算点唯一」这条结构成立，不涉及具体算法与阈值
- **配额的扣减与结算**。它是 `Outcome` 的下游消费者，本次留出接入点但不实现
- **Agent 层的任何编排逻辑**。模块壳建立，内容留给后续
- **从 `legacy/` 搬运任何实现代码**。本次不搬运，只准备搬运所需的对照能力
- **前端**。来源项目的前端本次不动
- **脱敏管线**。它依赖流式跨帧处理能力，本次不涉及
- **替换 OpenTelemetry 来源项目的 tracing**。本次不涉及

## Further Notes

**关于 GLOSSARY 与 ADR-0005 的一处用词差异，需要在实现时统一。**
`GLOSSARY.md` 中流式事件按 Opening / Delta / Terminal / Failed 四态分层，
而 ADR-0005 里给出的具体子类型列举更为展开（TextDelta / ToolCallDelta / Usage / Ping / …）。
本次以 GLOSSARY 的概念分层为准，具体子类型在实现时确定并回填至 GLOSSARY，
不应出现两份互相冲突的定义。

**关于缺失的基础文件。** 本仓库切换到新坐标系时把旧代码搬进了 `legacy/`，
根目录因此同时缺失构建文件与 `.gitignore`。后者本次一并补上
（`target/`、`.idea/`、`.DS_Store`、`.env*`）。

**关于操作顺序的一个强约束**：CI 与契约测试必须在任何 `legacy/` 代码被搬运之前就位。
这不是流程洁癖 —— Jackson 2 → 3 的静默变更只有在有了契约测试之后才可被识别，
在此之前搬运等于盲改。
