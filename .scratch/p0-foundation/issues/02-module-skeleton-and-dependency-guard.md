# 02: 四个模块骨架与依赖方向闸门

> 来源：[spec.md](../spec.md) — 用户故事 12、13、14

**What to build:** 四个模块在同一次构建里编译通过，并且结构性约束由机器判定而不是靠自觉 —— 有人让 `core` 依赖了某个框架、或者有人写了 `@Lazy`、字段注入、按类型 `getBean()`，构建会红。

这一步是把 ADR-0003 与 ADR-0006 里最容易被一句「先加个例外」稀释掉的两条约束，从文档搬进默认构建路径。刻意少写规则：规则越多，越容易走到「算了加个抑制」那条路上，来源项目那份 186 行抑制文件就是那条路的终点。

**Blocked by:** 01 根构建文件、Wrapper 与忽略规则

**Status:** ready-for-agent

- [ ] reactor 包含 `core`、`gateway`、`agent`、`app` 四个模块，`mvn clean verify` 在无源码内容的情况下也能编译全部模块
- [ ] `core` 模块的依赖树中不出现 Spring、Jackson、Reactor 或任何其他框架制品 —— 由一项依赖分析断言，出现即失败
- [ ] `agent` 模块是壳：足够让 `app` 把它装配起来，但不包含任何编排逻辑（本票不实现 Agent 行为）
- [ ] 没有模块可以依赖 `app`，由结构检查断言
- [ ] 源码中出现 `@Lazy`、字段注入、或按类型查找 bean 这三种写法时构建失败
- [ ] `gateway` 内部各包之间允许的引用方向被显式编码并强制执行；新增一处非法引用导致构建失败
- [ ] 结构检查运行在默认 `verify` 路径上，不在 profile 里、不需要手工执行某个 goal
- [ ] 反向验证存在：`gateway` 与 `app` 中正常使用框架注解不会被误伤，即门禁不能宽到让普通 Spring 写法也红
- [ ] 每条被编码的规则旁边有一行说明它保护什么，规则总数保持在个位数
