# 08: OutcomeObserver 结算与熔断器最小闭环

> 来源：[spec.md](../spec.md) — 用户故事 16、18、19、23

**What to build:** 连续的上游失败会让熔断器真的打开，打开之后的请求在本地快速失败而不是继续打到坏实例上；成败只有一个结算来源；未被纳入健康管理的实例不接收流量。为了让这些状态可被断言，顺带引入一个只读的运维查询面。

这条闭环修的是来源项目那个三跳缺陷：流式请求在写出响应头就算成功，于是实例只要还能返回半个 SSE 就永远健康，熔断器永不 OPEN。修法不是在散落的三处各补一句失败记录，而是让全链路只有 `OutcomeObserver` 一个结算点 —— 熔断器、健康管理、延迟统计都只消费 `Outcome`。

只读查询面（暴露每个实例的 CircuitState 与可用状态）不在原 spec 的 story 列表里，是为了让「熔断器真的开了」这件事能被机器判定才引入的。它后续也是运维层要消费的同一份数据。

**Blocked by:** 07 终态契约：失败、超时、取消三类结算

**Status:** ready-for-agent

- [ ] 连续若干次上游失败后熔断器进入 OPEN，此后的请求在本地快速失败，不再产生针对上游的出网调用（同时断言状态读值与「没有出网」两件事）
- [ ] 只读运维查询面返回每个实例的熔断器状态与可用状态；异常实例与正常实例在这里可以被区分
- [ ] 经过配置的冷却时间后熔断器进入 HALF_OPEN，一次成功的调用使其闭合
- [ ] 未纳入健康管理的实例不接收流量：配置漏项导致的实例缺失会立刻表现为不可用，而不是静默通过
- [ ] 客户端取消不算实例故障 —— 反复取消同一实例不会让它进入 OPEN（这条是对 ADR-0006 区分 cancellation 与 failure 的直接验证）
- [ ] 结构性规则：没有任何组件可以在 `OutcomeObserver` 之外提交成功或失败结论；新写一段自行判断 HTTP 状态码来决定成败的代码会让构建变红
- [ ] 同步路径与流式路径通过同一个观察者结算：本票内两类路径都要有对应的验证，不允许出现只对其中一条路径覆盖的情况
- [ ] 熔断器状态迁移带有请求标识，可以从一次失败追到它触发的那次状态变化
- [ ] 限流留出一个且仅一个决策点接口，由同一条管道消费；本票不实现具体算法与阈值
