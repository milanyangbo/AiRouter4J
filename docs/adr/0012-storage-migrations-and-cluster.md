# ADR-0012: 存储、迁移与多副本

- **状态**：已接受（新增，2026-10-25）
- **日期**：2026-10-25
- **相关**：[0001 目标态](./0001-project-scope-and-lineage.md)、[0002 技术栈](./0002-tech-stack-and-version-pinning.md)（Flyway + JDBC + Redis）、[0007 治理模型](./0007-traffic-governance-model.md)（共享计数与降级）、[0013 配置模型](./0013-configuration-model-and-runtime-registry.md)

## 背景

来源项目的持久化是它复杂度最集中的地方之一，也是它做得**最扎实**的地方之一 —— 两者同时成立：

| 做得扎实 | 复杂度失控 |
|---|---|
| Flyway 迁移与表结构（可搬的资产） | **4 套 store 并存 + 4 层 tier** |
| 调用历史三档 + AES-256-GCM | 4 套配置版本服务 |
| 多副本事件广播 / 共享计数 / 分布式锁 | 4 张配置版本化与审计表及周边 Service |
| 配额的 4 段 Lua 与 `usageStrict` | 热路径表（`service_config` / `service_instance` 含外键）**零索引**，而 45 个索引里相当比例建在日志表上 |

另一个背景是「什么时候接存储」。有一个看起来更稳的选项：先全内存，等链路稳定后再接存储。

## 决策

### 1. 存储一次到位：H2 默认 / PostgreSQL 按 `DATABASE_URL`

- 默认 H2（内嵌，零外部依赖即可启动）
- `DATABASE_URL` 指向 PostgreSQL 时切 PG
- **Flyway** 管 schema，两种方言各一份迁移

本机已跑着 **PG 16 + pgvector（`:5432`）** 与 **Redis 7（`:6379`）**，集成测试打真实实例而不是桩
（[0008](./0008-verification-and-quality-gates.md) 第 5 节）。

**为什么不是「先内存、后置存储」**：存储接入时要回头改所有写入方；
更要紧的是「Redis 挂了怎么办」这一**必测行为**会被无限期推迟 ——
而那恰恰是来源项目写得最好的一部分（`usageStrict`：读不到用量绝不当 0，否则凭空错杀请求）。

### 2. 「一次到位」不等于「强依赖」：缺席是契约，不是兜底

| 缺席方 | 行为 |
|---|---|
| **Redis 缺席** | 计数走本地后端；事件总线退化为本地；分布式锁退化为单机无锁。**启动日志明确说明降级生效** |
| **DB 缺席或不可用** | 运行时配置回落到内存 store；调用历史写入降级为不落库并记录 |

两条硬约束：

- **缺席路径本身是必测行为**，不是「测试环境没有 Redis 就跳过」
- 降级必须**可见**：静默降级等于把「保护是否生效」变成一个无法回答的问题

### 3. 只有一套 store，只有两类数据

不搬来源项目的 4 套 store + 4 层 tier。持久化数据只有两类：

1. **配置**（服务 / 实例 / 规则 / 网关策略）及其版本
2. **调用历史**（append-only）

判据：网关的持久化没有第三种形态。多套 store 的历史成因是「不同时期各加一套」，
不是「不同数据需要不同存储」—— 后者是设计，前者是沉积。

### 4. 迁移是 schema 的唯一变更路径

- 迁移脚本幂等，可重复执行
- **热路径表必须有索引**：`service_config` / `service_instance` 及其外键列
  取舍标准是**查询路径**而不是表的大小：日志表大但查询少，配置表小却在每次请求路径上被读取
- schema 变更不走「启动时自动更新」（JPA 的 `ddl-auto` 之类）：那会让生产环境的表结构
  取决于某次启动的顺序

### 5. 调用历史三档 + AES-256-GCM（搬来源项目的方案）

| 档 | 记什么 |
|---|---|
| `none` | 不记 |
| `metadata` | 只记元数据（时间、服务、实例、结果、耗时、用量） |
| `full` | 记完整请求与响应 |

完整内容用 **AES-256-GCM** 落库。两条硬约束：

- **解密端点仅 ADMIN**
- **密文不含明文回退**：解不开就是解不开，不存在「密文旁边还存了一份明文」这类降级

### 6. 多副本：Redis 承载三件事

| 能力 | 载体 | Redis 缺席时 |
|---|---|---|
| 共享计数（限流 / 配额） | Redis Lua 原子脚本 | 本地窗口，有额度上限与 TTL（[0007](./0007-traffic-governance-model.md) 第 5 节） |
| 事件广播（配置变更跨副本同步） | Redis 发布订阅 | 退化为本地广播（单机语义） |
| 分布式锁（配置热重载的互斥） | Redis，带租约与冷却 | 退化为单机无锁 |

锁的**租约与冷却必须可断言**：租约保证持锁者崩溃后锁会被释放，冷却保证不会因为时钟或 GC 抖动
让两个副本同时认为自己持锁。

### 7. 配置版本只有一套服务

来源项目有 4 套版本服务与 4 张版本化/审计表。本项目只有一套：
每次配置变更产生一个版本，可回滚。差异对比与「应用历史版本」属于 Phase C 的深化项，
但**版本模型在第一版就要对**，否则后面加回滚是在错误的基础上加。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 先全内存，后置存储 | 存储接入时要回头改所有写入方；「Redis 挂了怎么办」被无限期推迟 |
| 搬 4 套 store + 4 层 tier | 沉积而非设计；网关的持久化只有两类数据 |
| 引入 JPA / Hibernate 并开 `ddl-auto` | 生产表结构取决于启动顺序；且 ORM 是来源项目 store 复杂度的共谋者（[0002](./0002-tech-stack-and-version-pinning.md) 第 5 节） |
| Redis 缺席时静默降级 | 静默降级让「保护是否生效」变成无法回答的问题 |
| 密文旁存一份明文作回退 | 加密形同虚设 |
| 索引按表大小决定 | 热路径上的小表比大表更需要索引 |
| 每轮用 Testcontainers 起存储 | 本机已有常驻实例（[0008](./0008-verification-and-quality-gates.md) 第 5 节） |
| 多副本一致性用强一致协调（如 Raft） | 网关的共享状态是计数与事件，不是账本；为它引入协调器不成比例 |

## 后果

**正面**

- 存储与降级从第一天就是契约而不是补丁
- 集成测试打真实 Redis 与 PG，序列化差异、连接行为、事务语义都能被测到
- 只有一套 store，配置与调用历史的写入路径可数

**负面与风险**

- 测试时间会变长（真实存储比内存慢）；缓解方式是按 gate 分组跑
- H2 与 PG 两份迁移会漂移：同一份语义要在两种方言上各写一遍，改一处容易忘另一处。
  对策是**两种方言的集成测试都要跑**，而不是只跑默认的 H2
- Redis 降级窗口引入第二套额度语义，运维上要理解「本地额度」与「远端额度」的关系
- 调用历史是全库最大的表，三档策略如果不加治理会吃掉大量空间（Phase C 的保留策略要解决）

## 如何验证

- [x] 本机 Redis 7（`:6379`）与 PG 16（`:5432`）可用，集成测试指向它们
- [ ] H2 与 PostgreSQL 两种方言都能启动，且**两种方言的集成测试都要跑**
- [ ] 迁移脚本幂等，重复执行不改变结果
- [ ] Redis 缺席时启动成功、降级生效、**启动日志明确说明**，且该路径有断言
- [ ] DB 缺席时配置回落到内存 store，且该路径有断言
- [ ] 热路径表及外键列存在索引（迁移脚本静态检查）
- [ ] 调用历史三档可切换；`full` 档内容在库里是密文，**不存在明文回退**
- [ ] 解密端点仅 ADMIN 可访问（有测试）
- [ ] 分布式锁的租约与冷却可断言；Redis 缺席时退化为单机语义并被记录
- [ ] 配置版本只有一套服务，每次变更产生一个版本
