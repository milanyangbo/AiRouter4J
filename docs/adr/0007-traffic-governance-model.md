# ADR-0007: 实例维度、选择链与流量治理

- **状态**：已接受（第 2 版，2026-10-25 重写）
- **日期**：2026-10-25
- **相关**：[0006 流式终态](./0006-streaming-terminal-outcome-contract.md)（唯一输入）、[0003 模块结构](./0003-module-structure-and-dependency-direction.md)（`select` / `routing` / `governance` 的分工）、[0012 存储与多副本](./0012-storage-migrations-and-cluster.md)、[0013 配置模型与注册表](./0013-configuration-model-and-runtime-registry.md)

## 背景

来源项目的治理能力并不缺件 —— 限流、熔断、降级、健康检查、配额都有实现，
甚至包含 `LockFreeCircuitBreaker` 这样经过思考的并发设计。**问题不在缺，而在口径不一致**：

| 现象 | 后果 |
|---|---|
| 实例健康状态的默认值是**健康** | 从未被纳入健康管理的实例（配置漏项、刚注册未探测）会接收流量。这是 fail-open |
| **两套限流并存且零共享代码**：业务面 `router/ratelimit`（三级作用域 + 5 种算法）与管理面 `AdminApiRateLimiter`（一个 WebFilter，手写分钟/小时计数器） | 同一件事有两套语义、两套配置、两套故障模式 |
| 本地计数后端与 Redis 后端并存，一致性语义没有统一定义 | Redis 故障时是否放行、放多少，取决于具体代码路径 |
| 同一个默认值在两个方法里各写一遍，取值还不一致 | 不存在单一口径可查 |
| 配额在 Redis 故障时默认 **fail-open** | 限额整体失效，而这恰恰发生在依赖已故障的时刻 |
| 热路径表零索引（`service_config` / `service_instance` 含外键），45 个索引里相当比例建在日志表上 | 小表在每次请求路径上被全表扫 |
| 63 个权限码 / 83 条 URL 规则 / 4 个角色模板，URL 矩阵 + `@PreAuthorize` 双轨；WebFlux 下类级 `@PreAuthorize` 实际不可靠（它自己的注释承认，靠 URL 规则兜底） | 权限的真实生效路径与声明路径不一致 |

再叠加 [0006](./0006-streaming-terminal-outcome-contract.md) 那条：流式调用从不产生失败记录，
所以熔断器的输入本身是残缺的 —— **在修好输入之前讨论治理参数没有意义**。

## 决策

### 1. 治理层的输入只有一个来源

熔断器、限流回放、健康检查、延迟统计、配额结算，**全部只消费 `Outcome`**。
任何治理组件不得自己去看 HTTP 状态码、不得自己在 Reactor 操作符里判断成败、不得自己造一个 `Outcome`。
由结构规则 R4 / R9 判红，两条各有「故意违规」的样例保证真的会红。

### 2. 先有实例维度，才谈得上作用域

**服务 → 实例 → 形态** 三级（模型定义见 [0013](./0013-configuration-model-and-runtime-registry.md)）。
九类能力里有六类（负载均衡、规则路由、失败转移、限流作用域、配额维度、控制台的实例管理）
都以「一个服务下有多个实例」为前提。

在这个前提下：限流的作用域是 `global / service / instance / client`，
而这些标识在实例维度建立之前都不存在 —— 那时做限流，做出来的是一个全局开关。

### 3. 选择链只有一条，顺序被断言

```text
① 认证与租户识别（API Key / JWT → client 标识）
② 规则路由（条件匹配 → 目标服务，首命即止）
③ 可用性闸门（InstanceAvailability）：被纳入健康管理 ∧ 熔断未 OPEN ∧ 限流未拒绝
④ 实例选择（select）：从候选里挑一个（策略可插拔，纯函数）
⑤ 出网调用（transport）
⑥ 失败转移（请求级换实例重试，仅对可重试的失败）
```

三条硬性约束：

- **③ 只判一次**，判不过的请求**不出网、也不结算**（[0006](./0006-streaming-terminal-outcome-contract.md) 第 6 节）
- **④ 只能看到③筛过的候选**：策略是纯函数，不看健康、不做 IO
- **⑥ 的「重试算几次结算」必须有明确答案并被断言**：重试是同一次请求的不同尝试，
  结算只发生在最终那一次上；中间尝试计入指标但不重复扣配额

顺序本身是可测的：它落在 `routing` 的一处编排里，不是散在若干 handler 里。

### 4. 默认 fail-closed

**未被纳入健康管理的实例一律不可用。** 一个不知道是否健康的节点，和已知故障的节点，
对调用方造成的损害是一样的。fail-open 在这里只有「看起来还在跑」的假象。

配置漏项与「刚注册还没探测」落进同一侧，表现为不可用而不是静默放行 ——
这让遗漏在第一次请求时就暴露，而不是潜伏到流量高峰。

### 5. 限流与配额是**一个内核**，不是两套

| | 来源项目 | 本项目 |
|---|---|---|
| 业务面限流 | `router/ratelimit`，三级作用域 + 5 种算法 | 同一个内核 |
| 管理面限流 | `AdminApiRateLimiter`，一个 WebFilter，手写计数器 | 同一内核的**另一条入口**（作用域 = 管理面路径 / 管理员） |
| 配额 | 独立账本 + Lua | 同一内核，维度不同（token / 请求数 / 金额），窗口不同 |

一个判定接口 + 一组作用域 + 一组后端：

- **后端两级**：Redis（原子 Lua 脚本，单次判定、无读改写竞态）→ 本地降级窗口（**有额度上限、有 TTL**）
- **Redis 不可用**：进入本地降级窗口；本地额度耗尽后拒绝。理由是避免「Redis 故障 = 完全不限流」，
  但降级额度必须有上限与过期时间，不能变成一块永久的免检额度
- **算法可插拔**：`TokenBucket` / `SlidingWindow` / `LeakyBucket` / `WarmUp` 插在同一个端口下
  （这四种从来源项目搬，[0001](./0001-project-scope-and-lineage.md) 第 2 节「搬」的判据）

### 6. 配额搬来源项目的 Lua 与 `usageStrict`

来源项目配额最扎实的部分值得搬：**4 段 Lua 脚本** 与 `usageStrict` 语义。

`usageStrict` 的实质是：**读不到用量绝不当 0**。读不到时当 0 会凭空放行一批请求
（表现为限额整体失效）；而当「未知」则可以选择拒绝或降级。
它与 [0006](./0006-streaming-terminal-outcome-contract.md) 的取舍一致：少记一次与记成成功是同一种误导。

来源项目那段 fail-open 分层**不搬其默认值**，改为显式契约：
降级路径必须在配置里写明，且**缺席路径本身是必测行为**。

### 7. 熔断状态无锁更新，带版本号

保留 `LockFreeCircuitBreaker` 的思路（这部分来源项目做得对）：状态向量用 `AtomicReference` + CAS 更新，
并携带版本号防止 ABA —— 窗口期被计数清零又恢复的场景会让纯 CAS 误判为「状态未变」。

迁移记录里带着触发它的那个 `requestId`：能回答「谁把它打开的」，而不只是「什么时候开的」。

### 8. 认证与凭据隔离：网关凭据绝不透传给下游

- 客户端凭据（`X-API-Key` / JWT）用于识别 client，是限流与配额的维度之一
- **它绝不作为上游凭证发出**：上游凭证来自实例自己的配置（环境变量），与调用方无关
- 来源项目靠结构与文档保证这一点，**没有测试**。这里必须有

RBAC 的第一版不铺满 63 个权限码：先把来源项目的权限项**抄录并分类**（读 / 写 / 管理、按域分组）
作为待办台账，按需实现，并**只保留 URL 矩阵这一条轨**（WebFlux 下类级 `@PreAuthorize` 不可靠这一点
由来源项目自己的注释承认）。

### 9. 缓存只在确定性请求上生效

- 流式**默认不缓存**：流式的价值在于增量到达，缓存它会把延迟优势换成内存成本
- 缓存键必须含租户维度，且**租户退化的规则要被钉住**（无租户时键退化成什么，必须有确定答案）

### 10. 告警只出指标与结构化日志

仓内**不实现**任何推送通道（邮件 / Webhook / IM）。接入交给 Alertmanager 或日志平台。
这条要写成结构规则级别的可断言约束，否则「顺手加一个 Webhook」会在某个时刻发生。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保持 fail-open，靠配置规避 | fail-open 是默认值问题；只要默认是「健康」，任何遗漏都静默变成放行 |
| 限流与配额各自一套 | 来源项目已证明：两套并存 = 两套语义、两套配置、两套故障模式 |
| 管理面限流继续用独立 WebFilter | 同上；且它手写计数器的行为与业务面不一致 |
| Redis 故障时直接放行 | 在最危险的时候撤掉保护 |
| Redis 故障时完全拒绝 | 把 Redis 单点故障放大成全站不可用；本地降级窗口是中间解 |
| 本地降级窗口无上限 / 无 TTL | 变成一块永久免检额度 |
| 读不到用量就当 0 | 凭空放行；与「少记一次」是同一种误导 |
| 用 synchronized 保护熔断状态 | 治理状态在请求热路径上，锁竞争直接影响吞吐 |
| 每个治理组件各自订阅上游事件 | 回到 [0006](./0006-streaming-terminal-outcome-contract.md) 的根因：口径必然发散 |
| 缓存流式响应 | 把增量的延迟优势换成内存成本，且命中判定复杂 |
| 一次铺满 63 个权限码 | 变成配置搬运；且双轨里有一条在 WebFlux 下不可靠 |
| 仓内实现告警推送通道 | 与网关职责无关；开了口子通道就会增长 |

## 后果

**正面**

- 每类功能挂在同一条选择链上，作用域与判定顺序只有一处定义
- 限流、配额、熔断共享一个输入与一个内核，「同一个请求在 A 看来被限、在 B 看来没被限」不再可能
- fail-closed 让配置遗漏在第一次请求时暴露

**负面与风险**

- **选择链的顺序成为新的耦合点**：改顺序会影响所有作用域类功能，必须靠测试而不是靠人记得
- 本地降级窗口引入第二套额度语义，运维上需要理解「本地额度」与「远端额度」的关系
- fail-closed 降低容错外观：配置缺失表现为不可用。这是刻意选择的
- 限流内核要同时服务业务面与管理面，两条入口的语义差异（比如管理面按管理员限而不是按 client 限）
  会让内核长出配置项 —— 配置项增长是这条决定的主要风险

## 如何验证

- [x] 未纳入健康管理的实例不接收流量（`CircuitBreakerEndToEndTest`：漏配登记即不可用，反向验证会红）
- [x] 熔断 OPEN 后请求本地快速失败且不再出网；冷却后进 `HALF_OPEN`，一次成功闭合
- [x] 没有任何治理组件在 `OutcomeObserver` 之外获取成败（R4 / R9，各配违规样例）
- [x] 判定点只有一个（`ExactlyOneDecisionPointTest`）
- [ ] 选择链顺序有断言：限流拒绝不出网、不可选实例不进入 `select`
- [ ] Redis 不可用进入本地降级窗口，额度有上限与 TTL，耗尽后拒绝（**缺席路径必测**）
- [ ] 同一 `requestId` 重试只扣一次配额
- [ ] `X-API-Key` 不透传给下游（有专门测试，来源项目没有）
- [ ] 管理面与业务面限流走同一个内核（不存在第二个限流实现）
- [ ] 热路径表（`service_config` / `service_instance` 及外键列）有索引（迁移脚本静态检查）
- [ ] 仓内不存在任何告警推送通道（结构规则判）
- [ ] 流式默认不进缓存；无租户时缓存键的退化规则有确定答案
