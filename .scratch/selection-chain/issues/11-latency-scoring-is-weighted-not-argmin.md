# 11: `latency` 的打分口径是「按 1/(1+ewma) 加权」，不是 argmin

**What to build:** 把 `LatencySelector` 从「挑最快的那一个」改回 ADR 要求的「按延迟反比加权」，
并把「还没有样本的实例算哪一档」这件事一并裁掉 —— 两件事改的是同一段代码。

来源：两轴 code review（2026-10-28，固定点 `eedaff6`）的**两条独立发现**，两轴指到了同一行：

- ADR-0011 §2(d) 原句：*"…**权重 ∝ `1/(1+ewma)`**"*；§4 要的性质是「注入失败样本之后，
  那个实例被选中的概率**下降**」。票 10 落地的是 argmin
  （`observed[index] == fastest` 求最小集合，再让第 ④ 步在并列者里轮转）。
  差别不是「差不多」，是**性质变了**：慢的实例从「概率下降」变成**概率归零**（硬排除），
  于是 ADR-0011 §4 与 [spec](../spec.md) 故事 19/20 的「更可能」都不成立
- **注释在替它作证**：`LatencySelector` 类注释（第 18 行）与 `SelectionStrategy.LATENCY`
  的 javadoc 都写着 `1 / (1 + ewma)`，而代码里一次都没算。
  「文档与实现背离」比实现本身更贵 —— 看文档的人不会去读代码，而测试因为照着注释写，全绿
- 另一半是 **未知实例算哪一档**：[spec](../spec.md):155 写 *"延迟样本里还没有任何样本时
  `latency` 策略的行为是显式的（**不是把未知实例当成最快**）"*，票 10 写成了
  「0 毫秒 = 最好的一档」（probing，理由是「新机器要有机会被量到」）。
  两边不一致，**裁决结果要写回 spec 或 ADR-0011**，不是由本票单方面改向

## Acceptance criteria

- [ ] 打分是 `1 / (1 + ewma)`，**不是** argmin：每个候选拿到一个与延迟成反比的权重
- [ ] 有效权重 = 第 ④ 步的权重 × 上面那个系数。**不引入随机抽签** —— 随机源只有 `random`
      策略才有（它是注入进来的），`latency` 要能被**确定性**断言
- [ ] **本票存在的理由**：注入失败样本之后，那个实例被选中的**比例下降但仍然大于零**。
      argmin 的实现在这里给出的是 0 —— 「下降」与「归零」是两种性质，不是同一个数的两端
- [ ] 未知实例的档位**被裁决并写进 spec / ADR-0011**；代码、注释、文档三处一致
- [ ] 与 `LeastConnectionsSelector` 仍然共用的那段形状（打分 → 取子集 → 加权裁决）抽到一处，
      不留两份逐字重复的实现（两轴都指到了这段重复）
- [ ] 「换任意策略权重行为一致」那条断言覆盖到**五个**策略：`random` 用比例断言、
      `ip-hash` 用键占比断言（它们进不了「八次恰好 6:2」那种确定性形状，这要在断言旁边写明），
      一致哈希仍然不在这条里
- [ ] 注释与 javadoc 描述的是**实际在跑**的那套算法

## Known gaps（本票不做）

- 熔断与失败转移带来的**第三个**输入来源 → 阶段 7（ADR-0013）。本票不预留那个位置

- `least-connections` 的并列裁决也不动，本票只抽共用形状、不改它的语义

## 测试（两条接缝）

1. **单元接缝**（主）：`gateway/select/InputDrivenStrategiesTest` —— 注入样本后断言**比例区间**，
   不断言具体落点（testing.md 判据三：判性质，不抄实现）。区间要窄到能区分「加权」与「argmin」
2. **HTTP 入口**：票 10 建的那条端到端断言（`slowInstanceStopsReceivingTraffic`）**必须重新审视** ——
   它断言「最后四次都在快的那一个上」，而加权口径下慢的那个仍会拿到少量流量。
   本票要么把它改成「比例显著下降」之类的性质断言，
   要么在那个类里**写清楚**为什么它仍然可以是这个形状（两个实例相差两个数量级时的实测落点）
